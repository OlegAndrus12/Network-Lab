1. What the demo shows

Supports the slide «win» and the section «Керування швидкістю» (flow control): it makes “win = 0 → стоп” concrete.

  • server.py calls accept() and then does not call recv() for N seconds (or never).
  • client.py calls send() in a loop and prints progress. After about a quarter of a second the progress stops: send() is blocked. The client prints exactly how many bytes it handed to send(), how many are still in its own send buffer, and how many reached the server.
  • tcpdump shows the server advertising a shrinking window, then win 0, then the client's zero-window probes at growing intervals.
  • ss -tn (Linux) or netstat -an -p tcp (macOS) show the same thing from the kernel's side: Recv-Q grows on the server socket, Send-Q on the client socket.
  • Bonus: when the server finally starts reading, it sends a window update and the client un-freezes.

2. The mechanism

Where the bytes actually sit

client appsend() copies bytes into the kernel and returns
→
client send bufferSend-Q: bytes not yet ACKed (or not yet sent)
→
networksegments, limited by the peer's window
→
server receive bufferRecv-Q: bytes ACKed but not read by the app
→
server apprecv() would drain it… but it sleeps

send() does not mean “delivered”. It means “copied into my kernel's send buffer”. recv() does not fetch from the network; it copies out of the receive buffer, which the kernel filled long ago and already ACKed.

Flow control step by step

  1. Every segment the server sends carries win: how many more bytes it can accept right now, i.e. free space in its receive buffer. With window scaling (negotiated in the SYN/SYN-ACK, wscale 7 on Linux loopback) the real value is win × 2^wscale, so win 737 means 737 × 128 = 94 336 bytes.
  2. The server app never calls recv(), so the buffer fills and the advertised window shrinks: 94 336 → 14 464 → 0. The ACK with win 0 means: “I have everything up to byte N, but don't send more”.
  3. The client must stop. Unsent data piles up in its send buffer. Once the send buffer is full, send() blocks: the program freezes for a purely network reason.
  4. The danger: if the server's later “window is open again” ACK were lost, both sides would wait forever (the receiver doesn't retransmit pure ACKs). So the sender runs a persist timer (RFC 9293 §3.8.6.1, zero-window probing) and periodically sends a zero-window probe to provoke an ACK with the current window. Each unanswered-by-a-real-window probe doubles the interval (exponential backoff).
  5. When the app reads, buffer space frees up and the receiver sends a window update (a pure ACK with win > 0, same ack number). The sender resumes immediately.
  6. As long as the receiver keeps answering probes, the connection is not dropped: this can last indefinitely. That's the correct behaviour: the peer is alive, just slow.

Linux details (what you'll see in Docker)

  • Probe format. Linux sends a 0-byte segment with an already-acknowledged sequence number (snd_una − 1). The receiver must answer an out-of-window segment with an ACK, and that ACK carries the window. tcpdump shows it as Flags [.], ack 1, win 512, length 0 from client to server.
  • Interval. Starts at the RTO, which on loopback is the 200 ms minimum, and doubles: measured 0.208, 0.416, 0.848, 1.664, 3.328 s. Capped at 120 s.
  • Why the server's replies look irregular. The server's win 0 replies came at gaps of 0.208, 1.264, 1.664, 3.328 s: the reply to probe №2 is missing. Linux rate-limits ACKs sent in response to invalid/out-of-window segments (net.ipv4.tcp_invalid_ratelimit, default 500 ms). Probe №2 arrives 416 ms after the previous reply, so its answer is suppressed. I verified this by re-running with --sysctl net.ipv4.tcp_invalid_ratelimit=0: then every probe got a reply and the replies doubled cleanly (0.208, 0.416, 0.868, 1.661, 3.327). This is almost certainly why your own run showed “~0.2 s, 1.3 s, 1.7 s, 3.4 s”: those are the server's ack …, win 0 lines, and the client's probes in between doubled cleanly.
  • Numbers in Docker Desktop (kernel 6.12.76-linuxkit): receive buffer 131 072 (tcp_rmem default), of which 127 168 bytes of payload fit; the client handed 1 900 544 bytes to send() before blocking; 1 773 376 of them were still in its own send buffer (autotuned up to tcp_wmem max 4 MB). Your run's 2 883 584 / 128 512 had the same shape on a different kernel/sysctl set; don't promise students a specific number.

macOS details (what you'll see natively)

  • Sender-side silly-window avoidance. The macOS receiver stopped at win 242 (242 × 64 = 15 488 bytes free). That is less than one MSS (16 344 on lo0), so the macOS sender refused to send a small segment and waited. The client is frozen, but the window is not literally 0 yet.
  • Persist timer minimum is 5 s (BSD TCPTV_PERSMIN). After 5 s the sender pushed the last 15 488 bytes; only then did the server answer win 0.
  • Probe format. macOS sends 1 byte of new data beyond the window: seq 408705:408706 … length 1. The receiver drops the byte and re-ACKs with win 0.
  • Interval. Measured in a 70-s run: 5.04, 5.09, 5.08, 5.04, 5.00, 5.01, 7.14, 14.28 s. Clamped to at least 5 s; it starts doubling only when RTO × 2n exceeds 5 s (max 60 s).
  • Bigger buffers. The macOS server buffered 408 704 bytes although SO_RCVBUF reported 131 072 (receive-buffer autosizing). Shrinking SO_RCVBUF on macOS loopback hardly changes anything (with 16 KB requested it still buffered 326 720 bytes). Use Docker for small numbers.
Bottom line: the concept is identical on both OSes, but the Linux capture matches the slide (win 0 within 0.25 s, sub-second doubling probes). Run the Docker version for the main demo; mention macOS as “different implementation, same contract”.

cd ports/01-zero-window
./docker_demo.sh                                   # server sleeps 10 s, then reads
RCVBUF=16384 SNDBUF=16384 ./docker_demo.sh         # small numbers (~57 KB total)
READ_AFTER=0 ./docker_demo.sh                      # server never reads; client gives up after 8 s
DELAY=50ms READ_AFTER=12 ./docker_demo.sh          # netem delay: probes start later (~0.37 s), still double
PORT=9111 ./docker_demo.sh                         # other port

The first run builds the image (needs internet for apt-get). Do it before class. Duration of the default run: ~12 s.

B. macOS natively

./run_demo.sh                                       # works without tcpdump too
CAPTURE=sudo ./run_demo.sh                          # if you have sudo but no Wireshark/BPF access
READ_AFTER=40 ./run_demo.sh                         # long enough to see several 5-s probes

tcpdump runs automatically if you can read /dev/bpf0 (Wireshark's ChmodBPF / group access_bpf), otherwise it is skipped with a message and you still get the freeze plus the netstat snapshot.

5. Things to point out or ask students

  • “Where are the 1.9 MB right now?” Most students say “in the network” or “at the server”. Answer: 93% are still in the client's own kernel. send() returning ≠ delivered.
  • “Why did the program freeze if nothing is broken?” Because the receiver said win 0. TCP slows the fast sender down to the speed of the slowest application, not just the slowest link. That's flow control (rwnd), not congestion control (cwnd).
  • “What if the ‘window open’ ACK gets lost?” Deadlock. Hence the persist timer and probes. Ask them to spot the doubling in the timestamps.
  • “Why does the ack number not move?” Nothing new is accepted; ack 127169 repeats with every reply.
  • “Is the connection dead?” No: probes are answered, so TCP keeps waiting indefinitely. Contrast with a crashed peer (no answers → retransmission timeout → error).
  • Window scaling: win 737 is not 737 bytes. Multiply by 2wscale from the handshake.
  • Bonus (verified in Docker): if the client closes while frozen, close() returns immediately, but ss shows the socket in FIN-WAIT-1 with Send-Q 1773377 (data + FIN still waiting). close() doesn't mean delivered either.
  • READ_AFTER=0 ending: killing a server with unread data makes its kernel send RST, not FIN (visible as [R.]). Good link to the earlier handshake/close demo.
  • Real-world: a slow consumer (a DB client that doesn't read results, a stuck log shipper) freezes the producer the same way.

7. 1-minute fallback

  1. Open expected_output.txt, block 1 (Docker). Scroll to !!! send() ЗАБЛОКОВАНО: “1.9 MB sent, only 127 KB reached the server, the rest sits in the client”.
  2. Show the ss -tn lines right below: Recv-Q 127168 on the server, Send-Q 1773376 on the client.
  3. Show the explained capture at the end of block 1: the win 0 line, the five probes with 0.208 → 3.328 s doubling, and the green WINDOW UPDATE.
  4. Optional: open capture.pcap in Wireshark with the display filter tcp.analysis.zero_window || tcp.analysis.zero_window_probe || tcp.analysis.keep_alive || tcp.analysis.window_update. Checked with tshark 4.x: on the Linux capture Wireshark labels the server's lines “TCP Zero Window segment” and the window reopening “TCP window update”, but it labels the Linux probes “TCP keep-alive segment” (a 0-byte segment with an old seq number looks exactly like a keep-alive). On a macOS capture the 1-byte probes are labelled “TCP Zero Window Probe”.
