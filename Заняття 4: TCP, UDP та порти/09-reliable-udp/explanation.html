1. What the demo shows

We send 100 messages of 100 bytes over a deliberately bad network: tc netem on the container's loopback adds 25 ms delay per direction (RTT ≈ 50 ms), 10% loss, 5% duplication and 25% reordering. The same transfer runs four times, each time with one more piece of TCP built by hand on top of UDP:

#ScenarioWhat we addResult (one real run)
1naivenothing: 100 × sendto()97 datagrams arrive: 10 lost, 7 duplicated, 31 out of order. The sender has no idea.
2sawsequence numbers + ACK + retransmit timer (stop-and-wait)100/100 in order, but 8.65 s: 24 retransmits
3window+ sliding window of 16 packets, reorder buffer at the receiver100/100 in order, 1.67 s: about 5× faster
4tcpnothing: the kernel does it all100/100 in order, 0.10 s (up to ~1.2 s if the SYN is lost)

Slides it supports: «UDP — відправив і забув» and the TCP slide's list (sequence numbers, ACKs, retransmission, ordering, flow control). It also answers "if UDP is unreliable, how do QUIC, DNS, games and video calls work?" They add exactly as much reliability as they need, in the application.

2. The mechanism

The packet format

Every datagram starts with a 5-byte header: 1 byte type (DATA=1, ACK=2, FIN=3) + a 4-byte sequence number (struct "!BI" in common.py). DATA carries the message <MSG-17 ----…---- END-17>. No length prefix is needed: UDP already keeps message boundaries (demo 06), so one datagram is one packet.

What raw UDP does under netem (scenario 1)

netem acts on every packet leaving lo. With loss 10% a packet just disappears. duplicate 5% puts a second copy on the wire. reorder 25% sends a quarter of packets without the 25 ms delay, so they overtake the previous ones. The naive sender spaces datagrams 10 ms apart, so a packet that skips the delay overtakes the previous 2. UDP does nothing about any of this. The kernel delivers whatever arrives, in arrival order, and sendto() returned success for all 100.

Stop-and-wait (scenario 2)

Send one DATA, then wait for the ACK with that number. If nothing comes within RTO = 200 ms, send it again. The receiver ACKs every DATA, including duplicates, because the duplicate usually means "my previous ACK was lost". It delivers a number to the application only once.

The sender can't tell whether DATA or the ACK was lost. Both look the same: silence. A retransmit after a lost ACK shows up at the receiver as a duplicate. A retransmit after lost DATA does not. Duplicates also come from netem itself (duplicate 5%), so the two counters (24 retransmits, 21 duplicates dropped) don't map one-to-one. Throughput is capped at one message per RTT: 100 × 50 ms = 5 s, plus about 20 × 200 ms of timeouts ≈ 9 s. That matches the 7.5–8.7 s we measured.

Sliding window (scenario 3)

Allow up to 16 unacknowledged packets in flight, each with its own timer (selective repeat). The window's left edge base is the oldest unacknowledged number. It slides forward when that packet is ACKed. The receiver now sees gaps, because #10 arrives while #9 is still missing. It keeps #10… in a reorder buffer and hands them to the application only when #9 closes the gap. That is the "чекали в буфері: 75" line. 16 packets per RTT instead of 1 gives about 5× here. It's not 16×, because every loss still stalls the window for a 200 ms RTO.

Why TCP is still faster (scenario 4)

  • Bigger packets: TCP packs about 14 of our messages into one 1448-byte segment (we set lo MTU to 1500 like Ethernet), so it has about 7 segments to deliver instead of 100 datagrams.
  • Fast retransmit + SACK: TCP detects a loss from duplicate ACKs in about 1 RTT. It doesn't wait for a timer.
  • Adaptive RTO: TCP measures RTT and sets RTO from it (minimum 200 ms on Linux). Our RTO is a fixed guess.
  • But: a lost SYN costs the full initial RTO of 1 s. We saw 1.15–1.18 s in 2 of 5 runs. Reliability is not the same as low latency (see demo 04).

Our toy has no congestion control and no flow control. It will happily blast 16 packets into a congested network. That is the part that makes a homegrown protocol dangerous on the real Internet, and it's why QUIC re-implements TCP's congestion control on top of UDP.

3. Running it live

netem only exists in Linux, so run_demo.sh builds a small image and runs everything in one container with --cap-add NET_ADMIN.

cd ~/Projects/sandbox/ports/09-reliable-udp
./run_demo.sh                          # all: naive saw window tcp  (~15 s)
./run_demo.sh naive window             # just some of them
LOSS=20% ./run_demo.sh saw window      # more loss: the gap between saw and window grows
DELAY=25ms DUP=0% REORDER=0% ./run_demo.sh naive   # loss only
NO_DOCKER=1 ./run_demo.sh              # macOS, no netem: nothing is lost (baseline)

Manual, two terminals (students see both sides):

./run_demo.sh shell                    # container in background, netem already on
docker exec -it demo09-reliable-udp python3 receiver.py reliable      # T1
docker exec -it demo09-reliable-udp python3 sender.py window          # T2
docker exec -it demo09-reliable-udp tcpdump -i lo -n -tttt 'udp port 9109'   # T3, optional
./run_demo.sh stop

5. Things to point out or ask students

  • Before scenario 1, ask: "10% loss. How many of 100 will arrive, and will sendto() report an error?" Then point at "помилок ОС — жодної".
  • "Why does the receiver send an ACK for a duplicate it throws away?" Because the duplicate usually means the ACK was lost. Without a fresh ACK the sender retransmits forever.
  • "Was it the DATA or the ACK that got lost?" The sender can't tell. It only sees silence. The receiver can: a retransmit it has already seen means the ACK was lost. (Careful with arithmetic on the counters: netem's duplicate 5% also produces duplicates.)
  • "How do we choose RTO?" Too small: needless retransmits (spurious duplicates). Too large: long stalls. TCP measures RTT continuously (SRTT/RTTVAR, RFC 6298). Real run with --rto 0.03 (below the RTT): 86 retransmits, 66 useless duplicates, 186 DATA datagrams for 100 messages. It finished faster (4.75 s), but only by nearly doubling the traffic. On a shared network that is how a protocol causes congestion.
  • "Why is the window not 16× faster?" Every loss still costs a 200 ms timer, and the window can't slide past the hole. That's why TCP added fast retransmit and SACK.
  • "What's missing compared to real TCP?" Congestion control (we'd flood a busy link), flow control (receiver buffer size), adaptive RTO, connection setup, checksum over our header (UDP has one, but it's optional in IPv4).
  • "So who does this in real life?" QUIC/HTTP/3 (everything above + congestion control, in user space), DNS (just a retry timer), games and VoIP (seq numbers to drop stale data, no retransmits: demo 04), TFTP (literally stop-and-wait).

6. Gotchas and what to do if it misbehaves live

  • Docker not running / no internet for the first build: build the image before class (./run_demo.sh naive once). Fallback: section 7.
  • RTNETLINK answers: Operation not permitted: the container is missing --cap-add NET_ADMIN. run_demo.sh adds it. If you're running docker run by hand, add it yourself.
  • Conflict. The container name ... is already in use: ./run_demo.sh stop or docker rm -f demo09-reliable-udp demo09-reliable-udp-run.
  • Naive run shows 0 out of order: possible with REORDER=0%, or if you increased --gap above 25 ms (then nothing can overtake). Use the defaults.
  • Window not much faster than stop-and-wait: happens with very high loss (LOSS=40%). Every packet waits for timers. With the defaults the ratio was 4.4–5.2× in the three full runs we recorded.
  • TCP took ~1.2 s: the SYN (or SYN-ACK) was lost and Linux waited its 1 s initial RTO. Turn it into a teaching moment: run ./run_demo.sh tcp 3–4 times and compare.
  • NO_DOCKER=1 on macOS shows no losses: that's expected. It's a baseline that proves the code works. The losses come from netem, not from the code.
  • Python version: tested with macOS /usr/bin/python3 3.9.6 and Docker Python 3.12. No third-party packages.
