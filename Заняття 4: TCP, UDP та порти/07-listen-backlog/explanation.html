1. What the demo shows

Supports the slide «Життєвий цикл TCP-сокета» and exercise 8 (the note «Send-Q = backlog» for a listening socket).

A server calls listen(2) and then never calls accept(). Five clients connect. Students see that:

  • the kernel completes the three-way handshake on its own. The first clients are ESTABLISHED and have already sent data, although the program has not accepted them;
  • those finished connections wait in the listening socket's accept queue, which is visible: ss -ltn on Linux (Recv-Q = queue length, Send-Q = backlog) and netstat -Lan on macOS (qlen/incqlen/maxqlen);
  • clients that don't fit are stuck in SYN-SENT. Their SYNs are silently dropped and retransmitted (tcpdump shows this);
  • once the server starts calling accept(), the queue drains and the waiting clients get in on their next SYN retransmit.

Linux and macOS differ here in ways worth showing. All of the differences below come from real runs; see expected_output.txt.

2. The mechanism

listen() and accept() split the work

listen() puts the socket into LISTEN. From then on, the kernel answers SYNs, sends SYN-ACKs and receives the final ACKs. A fully established connection is put in the listening socket's accept queue. accept() does not do a handshake: it only takes the next finished connection off that queue and gives the process a new file descriptor. The backlog argument limits how long that queue may get.

client SYN ─▶ ┌─────────────────────────┐  final ACK  ┌────────────────────────┐ accept()
              │ SYN queue (half-open,   │ ──────────▶ │ accept queue (finished │ ────────▶ process
              │ SYN-RECV, "incqlen")    │             │ ESTABLISHED, "qlen")   │
              └─────────────────────────┘             └────────────────────────┘
                both limited by backlog                  full? new SYNs are dropped

A connection in the accept queue is a real TCP connection. Its receive buffer works: in our runs each waiting client's 16-byte message was ACKed by the kernel and shows as Recv-Q 16 on the server side, long before accept().

Linux (verified on kernel 6.12 in Docker)

  • For a LISTEN socket ss changes what its columns mean: Recv-Q = current accept-queue length, Send-Q = backlog (the value passed to listen(), capped by net.core.somaxconn; 4096 in the container). For every other state these are bytes in the buffers. This is the exercise 8 note.
  • The queue holds backlog + 1. The "full" check is queue length > backlog, so with listen(2) we saw Recv-Q 3 every time with the scripted clients.
  • When the accept queue is full, an incoming SYN is dropped silently: no RST and no SYN-ACK. The kernel counts it in TcpExtListenOverflows / TcpExtListenDrops (nstat). The client stays in SYN-SENT and retransmits. On this kernel (tcp_syn_linear_timeouts = 4) the retransmits came at about 1 s intervals at first, then 2, 4, 8 s. The client gets in on the first retransmit after accept() frees a slot, so the delay between "server accepts" and "client connects" is anywhere from 0 to several seconds.
  • The SYN queue is also limited by the backlog. When many SYNs arrive before any handshake completes (we forced this with a 50 ms netem delay and simultaneous connects), the SYN queue overflows first. With tcp_syncookies = 1 (the default) the kernel answers with a SYN cookie, a stateless SYN-ACK. The client completes the handshake and believes it is ESTABLISHED. When its ACK arrives the accept queue is full, so the kernel drops that ACK (tcp_abort_on_overflow = 0) and keeps no state at all: the server side shows no socket for these clients, not even SYN-RECV. The client keeps retransmitting its data. Each retransmit carries the cookie again, and after accept() frees space the next one creates the connection. Counters in that run: TcpExtSyncookiesSent 2, TcpExtSyncookiesRecv 8, TcpExtListenOverflows 8.
  • With tcp_syncookies = 0, the same burst just drops the extra SYNs (clients in SYN-SENT, like the normal case).
  • We did not observe the textbook "server in SYN-RECV retransmitting SYN-ACKs" state in any run. In both modes the kernel either dropped the SYN early or used a cookie. We did not test tcp_abort_on_overflow = 1 (it would send RST instead of silently dropping the final ACK).
  • Rare race: once, with 5 nc processes started at the same moment, Recv-Q reached 4 with backlog 2. The full-queue check is not atomic with adding to the queue, so simultaneous handshakes on several CPUs can overshoot. In 9 other runs it was 3.

macOS (verified on macOS 15, Darwin 24.6)

  • netstat -Lan -p tcp prints qlen/incqlen/maxqlen for each listening socket: finished connections waiting for accept / half-open connections / the limit. With listen(2) we saw 2/0/2: the queue holds exactly backlog, not backlog + 1. incqlen stayed 0 on loopback because the handshake completes instantly. kern.ipc.somaxconn is 128 on this Mac.
  • netstat -an has no special meaning for Recv-Q/Send-Q on LISTEN (it showed 0 0), so on macOS use -L for the queue.
  • Overflowing clients sit in SYN_SENT. Their SYNs are dropped silently, as on Linux, but the retransmit timing is very different on loopback: about every 30 ms for the first five, then doubling (60, 120, 240, 480 ms, 1 s, 2 s, 2 s). After 13 SYNs in about 6 seconds the client gives up with ETIMEDOUT. Our interpretation (not verified in XNU source): the BSD stack allows 12 retransmits, and the loopback RTO is tiny, so the 12 retransmits are used up within seconds. On a real network the same 12 retransmits would take much longer.
  • After a few retransmits macOS drops the window-scale and timestamp options from the SYN (seen in the raw tcpdump), a fallback for middleboxes that drop unusual SYNs.
  • netstat -s -p tcp showed 0 listen queue overflow even after overflows in our runs, so don't use it as evidence.

3. Running it live

Before class: build the Docker image once while you have internet: docker build -t demo07-backlog . in the folder (or just run ./run_docker.sh once). Do one dry run of ./run_demo.sh on the lecture laptop.

Option A: one command (recommended)

cd 07-listen-backlog
./run_demo.sh                    # macOS or Linux; press Enter when you want accept() to start
AUTO=1 ./run_demo.sh             # no Enter: accept() starts 1 s after the queue snapshot
N=8 BACKLOG=3 ./run_demo.sh      # other numbers
PORT=9117 ./run_demo.sh          # spare port

Steps it prints: === 1 server and clients start; === 2 queue snapshot (netstat -Lan and netstat -an on macOS; ss -ltn, ss -tan, nstat on Linux); Enter; === 3 accept() and draining; === 4 snapshot again; === 6 per-client SYN and data counts from tcpdump.

macOS: press Enter within about 4 s of the snapshot. The waiting clients give up about 6 s after their first SYN. If you are slower, they print ETIMEDOUT. That is a fine teaching moment as well (see run D in expected_output.txt), but if you want to show the drain, be quick or use AUTO=1.

Option B: Linux in Docker

./run_docker.sh                         # normal: extra clients in SYN-SENT, ss shows Recv-Q 3 / Send-Q 2
./run_docker.sh cookies                 # 50 ms delay + simultaneous connects: SYN-cookie case
SYNCOOKIES=0 ./run_docker.sh cookies    # same burst, cookies off: back to SYN-SENT
AUTO=1 ./run_docker.sh                  # no Enter

On Linux the drain can take a few seconds (next SYN retransmit), so the script waits 10 s (DRAIN=10) before the second snapshot.

Option C: by hand, with nc (more "live")

macOS, three terminals in the folder:

# Terminal 1: server
python3 server.py                         # listen(2), waits for Enter

# Terminal 2: five clients (-d: nc does not read stdin)
for i in 1 2 3 4 5; do nc -d 127.0.0.1 9107 & done

# Terminal 3: look at the queue
netstat -Lan -p tcp | grep 9107           # 2/0/2  = qlen/incqlen/maxqlen
netstat -an -p tcp | grep '\.9107 '       # 2 pairs ESTABLISHED + 3 SYN_SENT
lsof -nP -iTCP:9107                       # same, with process names

# Terminal 1: press Enter -> accept() No 1, 2, then 3, 4, 5 as their SYNs get through
# cleanup (terminal 2):
pkill -f 'nc -d 127.0.0.1 9107'

Use nc -d. Without it, and with stdin at EOF, macOS nc sends FIN right after connecting (we saw CLOSE_WAIT/FIN_WAIT_2 on connections still in the queue). Without -d in an interactive shell, a background nc that tries to read the terminal may also be stopped by the shell. Remember the 6-second window on macOS for the three waiting ncs.

Linux in Docker, two terminals:

# Terminal 1
docker run --rm -it --name demo07-lab --cap-add NET_ADMIN --cap-add NET_RAW \
  -v "$PWD":/demo demo07-backlog bash
python3 server.py

# Terminal 2
docker exec -it demo07-lab bash
tcpdump -i lo -n 'tcp port 9107' &       # optional: watch the SYN retransmits
for i in 1 2 3 4 5; do nc -d 127.0.0.1 9107 & done
ss -ltn 'sport = :9107'                   # LISTEN  Recv-Q 3  Send-Q 2
ss -tan '( sport = :9107 or dport = :9107 )'
nstat -az TcpExtListenOverflows TcpExtListenDrops
# Terminal 1: Enter. Then ss -ltn again: Recv-Q 0

On a native Linux laptop the same commands work without Docker. run_demo.sh starts tcpdump only if you are root; otherwise it skips the capture.

5. Things to point out and ask

  1. "Who did the handshake?" Not the program: it never called accept(). The kernel did. Clients 1–3 even sent data, and the kernel ACKed it (Recv-Q 16 on the server side).
  2. Exercise 8: point at LISTEN 3 2. For a listening socket Send-Q is the backlog and Recv-Q is the queue. Ask: "Why 3 and not 2?" (Linux keeps backlog + 1; macOS showed exactly 2.)
  3. "What does the server send to client 4?" Nothing. No RST and no SYN-ACK: the SYN is just dropped. Ask why dropping is better than refusing (RST would make the client fail immediately; a drop makes it retry, which is right for a momentary overload).
  4. "Why didn't client 4 connect the instant accept() ran?" The server doesn't call anybody back. The client gets in on its next SYN retransmit. This is where "the site loads after exactly 1 s / 3 s" latency comes from on overloaded servers.
  5. Same API, different OS: macOS gave up after about 6 s on loopback; Linux clients were still retransmitting SYNs after 19 s in our runs (we did not wait for the Linux give-up). Both are valid TCP.
  6. Cookie case (optional, advanced): the client believes it is ESTABLISHED while the server has no record of it. Connected does not mean accepted. Link to SYN floods: SYN cookies exist so a full SYN queue doesn't lock out real clients.
  7. Real servers: a server that is slow to accept() (blocked event loop, all workers busy) looks exactly like this from outside. That's why backlog is a tuning knob (Nginx and Node.js use 511 by default on Linux) and why somaxconn matters.

6. Gotchas and recovery

SymptomCause / what to do
macOS: waiting clients print ETIMEDOUT before you press EnterThe 6-second window. Explain it ("the client gave up after 13 SYNs") and rerun with AUTO=1 ./run_demo.sh.
Linux: after Enter, clients 4–5 take several secondsExpected: they get in on the next SYN retransmit (up to 8 s later if you waited long). The script waits 10 s.
Address already in useAn old server.py is still running: pkill -f server.py, or use PORT=9117.
Lots of TIME_WAIT lines in manual netstat/ssLeftovers from the previous run (server closed first). The scripts filter them out; in manual mode add | grep -v TIME_WAIT.
Linux shows Recv-Q 4 with backlog 2A rare race with simultaneous connects (seen once with 5 parallel nc). Just say "the limit is approximate under races" or rerun.
Step 6 (SYN counts) missingtcpdump needs root on Linux, or /dev/bpf* access on macOS (Wireshark's ChmodBPF / access_bpf group). Without it the capture is skipped; the rest of the demo still works.
nstat numbers bigger than expectedOn a native Linux host they are system-wide counters. In Docker they count from container start, so run_docker.sh starts at 0.
run_docker.sh hangs at buildNo internet for apt-get. Build the image in advance, or fall back to macOS plus expected_output.txt.
Wrong Python / odd errorsThe scripts use python3 from PATH (3.9+ works). Override with PYTHON=/path/to/python3 ./run_demo.sh. A python3 shell alias or function is not visible inside the bash scripts.
Need to stop everythingCtrl+C in run_demo.sh kills the server, the clients and tcpdump. Manual mode: Ctrl+C in the server, pkill -f 'nc -d 127.0.0.1 9107', and docker rm -f demo07-lab.

7. 1-minute fallback

Open expected_output.txt and walk through three spots:

  1. Section B, step 2 (Linux): LISTEN 3 2, three ESTAB pairs with Recv-Q 16, two SYN-SENT. "The program never accepted, yet three clients are connected; two are knocking."
  2. Section C: the same SYN four times on Linux, twelve times on macOS, then the SYN-ACK once accept() frees a slot.
  3. Section A, steps 2 and 4 (macOS): 2/0/2 becomes 0/0/2, and the server prints accept() №1…№5.
