1. What the demo shows

A server on port 9103 sends a file to a client over loopback inside a Linux container. We add 100 ms of delay with tc netem, so the round trip is 200 ms and every step of TCP's growth is slow enough to watch. A sampler polls ss -tin every 20 ms on the server socket, because the server is the sender and the congestion window lives on the sender. It prints one row each time cwnd changes. Students see the window go 10 → 20 → 40 → 80 → 160 → 320 → 640 → 1280 segments, one doubling every ~200 ms. That is the cwnd table from «Керування швидкістю», with real numbers and real timestamps.

A second run (--loss) sends 24 MB, which is enough to see what happens after slow start. A packet loss appears, ssthresh gets set, retransmissions are counted, and growth switches to the slow congestion-avoidance phase. The same transfer is captured to a .pcap, so Wireshark's Stevens graph (Statistics → TCP Stream Graphs → Stevens) can draw the same staircase.

2. The mechanism

Two windows, one limit

A TCP sender may have at most min(cwnd, rwnd) bytes unacknowledged ("in flight"). rwnd is what the receiver advertises: how much buffer it has free. cwnd is the sender's private guess at how much the network can absorb. The receiver never sees it, and it never appears in any packet. That is why we read it from the sender's kernel with ss, not from the wire. Linux keeps cwnd in segments of one MSS each. Here MSS = 1448 bytes: MTU 1500 minus a 20-byte IP header, a 20-byte TCP header and 12 bytes of timestamp option.

Slow start

  • Initial window = 10 segments (RFC 6928, the Linux default since 2.6.39). That is the first row of the table.
  • +1 segment of cwnd for every segment acknowledged. A full window of N segments gets acknowledged within one RTT, so cwnd becomes 2N: it doubles once per RTT. The growth is exponential. It is called "slow" only by comparison with pre-1988 TCP, which sent a whole receiver window at once.
  • Linux counts segments acknowledged, not ACK packets (in the spirit of RFC 3465). This matters because the receiver ACKs far less often than once per segment. In our recorded capture there are 2173 data segments but only 380 ACKs, and the doubling is still exact.
  • ssthresh starts at "infinity". ss prints nothing for it until the first congestion signal. Slow start ends when (a) a loss is detected, (b) cwnd reaches ssthresh, or (c) for CUBIC, HyStart sees the RTT rising or an ACK train that is too long, and exits early to avoid overshooting.

After a loss (CUBIC, the Linux default)

  • CUBIC sets ssthresh = 0.7 × cwnd (β = 0.7; classic Reno halves to 0.5). During recovery Linux lowers cwnd gradually (Proportional Rate Reduction) and retransmits the missing segments (SACK/RACK). That is why the table shows odd values like 205 or 1156 while retrans is non-zero.
  • After recovery cwnd ≈ ssthresh and growth is congestion avoidance: a cubic function of time since the loss. In our run that was about +10 to +20 segments per RTT (×1.01), against ×2 in slow start.
  • Loss is detected roughly one RTT after it happens, because the sender learns of it from duplicate or SACK ACKs. Meanwhile slow start keeps doubling, so cwnd overshoots. That overshoot is the burst of losses you see.

Why netem on lo delays both directions, so the RTT is 200 ms, not 100 ms

tc qdisc add dev lo root netem delay 100ms attaches netem as lo's egress qdisc. On a physical NIC, egress means "leaving this host", so it delays only one direction. On loopback, every packet is transmitted by the lo device and then looped back as a received packet. Both the server's data segments and the client's ACKs go through lo's transmit path, so each one waits 100 ms. RTT = 100 + 100 = 200 ms. The real output agrees in three independent places:

  • the client prints рукостискання зайняло 202 мс (the handshake took 202 ms: SYN → SYN-ACK is one round trip);
  • ss reports rtt:201.9…202.5 ms, plus about 2 ms of processing;
  • in the pcap the SYN-ACK is 100.9 ms after the SYN, and the final ACK is 101.0 ms after the SYN-ACK.

tcpdump on lo sees each packet once, when lo transmits it, i.e. after the netem delay. The pcap timestamps therefore already include the delay.

CUBIC is fine for this demo. In slow start CUBIC behaves exactly like Reno: +1 per ACKed segment. Its cubic curve only applies after the first loss. With a constant netem delay, HyStart normally does not fire (counter 0/0 in all recorded runs). In one exploratory run it did fire, at RTT 238 ms, when the CPU was busy. No congestion-control change is needed.

Where the loss in --loss comes from (honest version)

The loss is not random, and netem does not inject it. netem releases a whole window of delayed packets at the same instant. On loopback they all land in the per-CPU receive backlog queue (net.core.netdev_max_backlog, default 1000 packets). Once a window exceeds roughly 1000 to 2000 segments, the backlog overflows. This works like a router's buffer overflowing, which is a real congestion loss. The script prints both counters, and in every recorded run they matched exactly: TcpRetransSegs 247 = softnet backlog drops 247 (another run: 1196 = 1196). The exact moment and the ssthresh value vary from run to run (we saw 1477, 1737, 2293 and 2907), so don't promise students a specific number for this part.

macOS: what differs

  • macOS has no ss and no unprivileged per-socket cwnd view. netstat -an -p tcp, lsof -nP -iTCP:9103 and nettop -m tcp show sockets, states, bytes and RTT, but not cwnd. Tools that do show it (dtrace, netstat -s aggregates) need root or SIP changes, and we did not use them.
  • macOS also uses CUBIC (net.inet.tcp.use_newreno: 0, cubic_sockets: 78), so the principle is the same.
  • Delay on macOS would need dnctl/pfctl (dummynet), which requires sudo. Not tested.
  • Without delay, a run on the Mac host finishes 200 MB in 0.04 s (real run): the loopback RTT is microseconds, and slow start is over in under a millisecond. This makes a good 10-second contrast. Then switch to Docker.

3. Running it live

Before class (once, about 1 minute)

cd ~/Projects/sandbox/ports/03-slow-start
docker info > /dev/null && echo "Docker OK"   # Docker Desktop must be running
./run_demo.sh                                  # first run builds image demo03-slowstart (~30 s)

Option A: one command (macOS or Linux, both go through Docker)

./run_demo.sh            # clean slow start: 3 MB, delay 100 ms, MTU 1500. Takes ~3 s
./run_demo.sh --loss     # 24 MB: slow start, then loss, ssthresh, congestion avoidance. ~6 s

The table prints row by row as it is sampled (one row per RTT). It is followed by the client summary, the kernel counters, the per-RTT segment counts taken from the pcap, and the location of capture.pcap. Each run overwrites cwnd_table.txt and capture.pcap; the reference copies in recorded/ are never touched. Other flags: --delay 50, --size-mb N, and for comparison --mtu default and --default-rmem.

Option B: by hand with watch (closest to the slide's command), 4 terminals

# Terminal 0: start the lab container and configure lo (delay, MTU, offloads)
docker run -d --rm --cap-add NET_ADMIN --sysctl net.ipv4.tcp_rmem="4096 4194304 6291456" \
  --name demo03-live -v "$PWD":/demo -w /demo demo03-slowstart sleep infinity
docker exec demo03-live ./setup_net.sh 100 1500

# Terminal 1: server, serves any number of clients, 16 MB each
docker exec -it demo03-live python3 server.py --size-mb 16 --clients 0

# Terminal 2: the raw kernel view from the slide (note -n, see Gotchas)
docker exec -it demo03-live watch -n 0.2 "ss -tin '( sport = :9103 )'"

# Terminal 3: the clean table (optional, prints one row per change)
docker exec -it demo03-live python3 sampler.py

# Terminal 4: start the download; repeat as often as you like
docker exec -it demo03-live python3 client.py

# afterwards
docker rm -f demo03-live

In the watch pane, point at cwnd:, rtt:, unacked:, and retrans: (that last one appears only after a loss). Start the sampler before the client: it waits up to 60 s for a connection and exits after the transfer. A 16 MB transfer lasts ~3 s, so the watch pane only shows 10 to 15 frames. Use --size-mb 40 if you want it on screen longer.

Linux host without Docker

Don't run setup_net.sh on your own machine. Delay on the host's lo slows down everything on localhost (databases, IDE language servers…). If you must avoid Docker, use a network namespace instead (sudo ip netns add demo03, then sudo ip netns exec demo03 bash, then ip link set lo up). We did not test this here, because the host is a Mac without passwordless sudo.

Wireshark: Stevens graph (on the Mac)

brew install --cask wireshark       # not installed on the test Mac, so this step is untested
open -a Wireshark recorded/capture_default.pcap      # or capture.pcap from the last run

Click a data packet from port 9103 (length 1448), then Statistics → TCP Stream Graphs → Stevens. If the plot is flat, you selected the ACK direction: press "Switch Direction". Each vertical step is one window of segments sent back-to-back. The steps are 200 ms apart and double in height. recorded/capture_loss.pcap shows the loss and the retransmissions too. The capture has headers only (snaplen 96), which is enough for every TCP graph.

5. Points to make and questions to ask

  • "Why does it start at 10 and not at 1?" IW10, RFC 6928 (2013). Older textbooks show 1 or 2. Ask what difference that makes to a 15 KB web page: 10 × 1448 = 14 480 bytes fits in the very first RTT.
  • "How many RTTs to reach 1280?" log₂(1280/10) = 7. Check against the table: 7 rows × ~200 ms ≈ 1.43 s. Then ask what the same file costs on a 20 ms RTT: ~0.14 s. RTT, not bandwidth, dominates short transfers. This is why CDNs exist and why HTTP/2 and HTTP/3 reuse connections.
  • "We set 100 ms. Why does it say 200?" Both data and ACKs cross lo (see section 2).
  • "Who decides cwnd: client or server?" The sender, i.e. the server here. cwnd is not in any header, which is why Wireshark can only infer it from bytes in flight.
  • "Why is it called slow?" Compared with blasting the whole receive window at once, which is what caused the 1986 congestion collapse that led Van Jacobson to design these algorithms.
  • "After the loss, why 0.7 and not half?" CUBIC's β = 0.7, against Reno's 0.5. Both are AIMD-style "back off multiplicatively".
  • Show the --default-rmem table (expected_output.txt, section 3): cwnd can be big while unacked stays small. The receive window was the limit. This links to the rwnd part of the same slide.
