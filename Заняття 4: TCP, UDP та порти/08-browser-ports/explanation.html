1. What the demo shows

Supports the slide «Порт — номер процесу на хості» and the QUIC / 443/udp point. Students open YouTube and list their own browser's sockets. They see:

  • many TCP connections to remote port :443, each with its own local ephemeral port (49152–65535 on macOS/Windows, 32768–60999 on Linux);
  • in Chrome (and other Chromium browsers), UDP sockets to :443. That is QUIC, the transport under HTTP/3;
  • that all of these belong to one process (on macOS, Chrome's network service helper), which is the point of the slide: the port number tells the OS which process gets the data.

It takes 2–3 minutes, and it is about their own machines, which makes the theory stick.

2. The mechanism

A port identifies a process's socket on a host

An IP address gets a packet to the host. The port gets it to a socket, and the socket belongs to a process. The kernel picks the socket by the 5-tuple (protocol, local IP, local port, remote IP, remote port). The server side is always :443; the client side is a different ephemeral port the kernel picked at connect() time. That is why one browser can have 20 connections to the same :443 on the same server with no confusion: every local port is different.

Why QUIC runs over UDP

  • TCP can't be changed in practice. It lives in OS kernels, and middleboxes (NATs, firewalls) inspect and rewrite TCP headers. A new transport protocol number would be dropped by most of them. UDP passes through almost everywhere, so QUIC uses UDP as a thin envelope and implements reliability, ordering, congestion control and flow control itself, in user space (inside the browser). It can ship with each browser release.
  • No head-of-line blocking between streams. HTTP/2 multiplexes many requests over one TCP connection; one lost TCP segment stalls all of them, because TCP delivers one ordered byte stream. QUIC has independent streams, so a loss stalls only the affected stream.
  • Faster setup. TCP handshake + TLS 1.3 = 2 round trips before data. QUIC merges the transport and TLS 1.3 handshakes into 1 RTT, and 0-RTT on resumption.
  • Connection migration. A QUIC connection is identified by a connection ID, not the 4-tuple, so it survives a change of IP/port (Wi-Fi to mobile, NAT rebinding). A TCP connection would break.
  • Almost everything is encrypted, including most of the transport header. That is also why tcpdump/Wireshark show only "UDP 443" without the browser's TLS keys.

How the browser finds out: the first visit typically goes over TCP (HTTP/2). The server advertises Alt-Svc: h3=":443" (or an HTTPS DNS record), and Chrome then races a QUIC connection. If UDP/443 is blocked, it silently stays on TCP. So seeing no UDP :443 is a valid result, not a failure.

The UDP "connection" in lsof (UDP local->remote:443, no state) is a connected UDP socket: the app called connect() on a UDP socket, which only fixes the peer address in the kernel. No packets are exchanged by that call. The connection state lives in QUIC, inside the browser.

Where the sockets live on macOS

Chromium browsers do networking in a separate network service process, not the main window process. On this Mac (Chrome 155) it is Google Chrome Helper (Aperitif) with --utility-sub-type=network.mojom.NetworkService (check with ps -o args= -p <PID>). Safari's sockets belong to com.apple.WebKit.Networking.

Main gotcha, verified on this Mac: lsof -i -P -n | grep -iE 'chrome|safari' finds 0 lines. lsof on macOS truncates COMMAND to 9 characters and encodes spaces as \x20, so Chrome's helper appears as just Google, and Safari's as com.apple. 3. Running it live

Before class: run ./run_demo.sh once on the projector machine; have YouTube playing in Chrome for a few seconds before you run it.

macOS

cd 08-browser-ports
./run_demo.sh                 # anonymised IPs: safe on the projector
ANON=0 LINES=25 ./run_demo.sh # real IPs, more lines

# the bare commands for students:
lsof +c 0 -i -P -n | grep -iE 'chrom|safari|webkit|firefox|brave|edge|browser' | head -20
lsof +c 0 -i -P -n | grep -iE 'chrom|webkit|firefox|brave|edge|browser' | grep UDP | grep ':443'   # QUIC only
lsof -a -c '/chrome|webkit|firefox|brave|edge/i' -i -P -n     # same filter via lsof itself (-a = AND)
python3 browser_ports.py --anonymize --lines 15

sysctl net.inet.ip.portrange.first net.inet.ip.portrange.last
netstat -anv -p udp | grep '\.443 '        # UDP :443 with rxbytes/txbytes and pid columns
nettop -m udp -L 1 -n -p <PID>           # per-socket bytes for one process (CSV, one sample)
nettop -m tcp                              # interactive, live; q to quit

Flags: -i internet sockets, -P numeric ports (443, not https), -n no reverse DNS (much faster), +c 0 full process name.

Linux

ss -tunp | grep ':443'                          # t=TCP u=UDP n=numeric p=process
ss -unp 'dport = :443'                          # UDP :443 only = QUIC
ss -tnp state established '( dport = :443 )'    # TCP :443 only
cat /proc/sys/net/ipv4/ip_local_port_range
lsof -i -P -n | grep -iE 'chrome|firefox|brave|msedge' | head    # if lsof is installed
python3 browser_ports.py --anonymize --lines 15

./linux_check.sh    # from the Mac: Linux range + lsof/ss output in Docker (needs internet for apt)

Note: in ss, a connected UDP socket shows state ESTAB. UDP still has no connection; it means only that connect() fixed the peer address.

Windows (not tested here)

:: cmd
netstat -ano | findstr :443
tasklist /FI "PID eq 1234"                  :: which process owns PID 1234
netstat -ano -p udp                         :: UDP endpoints (foreign address shows *:*)
netsh int ipv4 show dynamicport tcp         :: ephemeral range

# PowerShell
Get-NetTCPConnection -RemotePort 443 -State Established |
  Group-Object OwningProcess |
  Select-Object Count, @{n='Process';e={(Get-Process -Id $_.Name).ProcessName}}
Get-NetUDPEndpoint | Where-Object { (Get-Process -Id $_.OwningProcess).ProcessName -match 'chrome|msedge|firefox|brave' }

On Windows, UDP endpoints don't show the remote address, so QUIC can't be identified by "remote port 443" there. Use the browser views below. The TCP part works the same.

Seeing HTTP/3 in the browser (any OS)

  • DevTools → Network, right-click a column header → enable Protocol. Reload YouTube: h3 = HTTP/3 over QUIC (UDP), h2 = HTTP/2 over TCP, http/1.1. Works in Chrome, Edge, Brave, Arc and Firefox (Firefox shows HTTP/3).
  • chrome://net-internals/#quic: list of active QUIC sessions (Chrome has removed several net-internals tabs over the years, so check it on your Chrome version beforehand). chrome://net-internals/#sockets shows socket pools.
  • Live toggle: chrome://flags/#enable-quic → Disabled → relaunch. The UDP :443 lines disappear and TCP :443 takes over. Good optional proof that QUIC is a separate transport.

5. Things to point out and ask

  • "Which column is the server, which is you?" Left of -> is local (ephemeral port), right is remote (443). Same server, same 443, different local ports: that is how the kernel tells the connections apart (5-tuple).
  • "Why does one process have 20 sockets?" Separate origins (youtube.com, googlevideo.com CDN, fonts, analytics), each with its own connection. HTTP/2 and HTTP/3 multiplex many requests over one connection per origin, so it is not one socket per request.
  • "UDP to port 443? Isn't 443 HTTPS over TCP?" Port numbers are per protocol: 443/tcp and 443/udp are different ports. IANA assigned both to HTTPS; 443/udp is HTTP/3.
  • "Why do UDP lines have no (ESTABLISHED)?" UDP has no connection state in the kernel. QUIC keeps its state inside the browser.
  • "Compare your range with your neighbour's" (Mac/Windows vs Linux: 49152+ vs 32768+).
  • "Who has zero UDP :443?" Firewall blocking UDP/443, VPN, Safari/Firefox not choosing h3 for that site. The browser quietly fell back to TCP: an example of why QUIC was designed with fallback.
  • "What is :5353 / :5228?" mDNS (finding Chromecasts etc. on the LAN) and Google's push channel. Ports name services, not just "web".
  • Quick count: run it twice, 30 s apart. The ephemeral ports change as connections close and open.

7. 1-minute fallback

If the network or laptop misbehaves: open expected_output.txt and walk through it.

  1. Section A, step 1: the plain grep finds 0 lines; with +c 0, 21 (10 s).
  2. Step 2: point at one UDP ...->:443 line (QUIC) and the four TCP lines to the same server with different local ports (20 s).
  3. Step 3 summary: 5 TCP :443, 3 UDP :443, all local ports inside 49152–65535 (15 s).
  4. Section B: 3.4 MB received over one UDP :443 socket. That is video over HTTP/3 (10 s).
  5. Section C: Linux range 32768–60999 for comparison (5 s).

Remote IPs in the file are documentation addresses (RFC 5737), not real servers. Say so if a student tries to look them up.
