Демо 08: порти вашого браузера просто зараз

Тема 4. TCP, UDP та порти. Нотатки лектора, папка 08-browser-ports/. Слайди: «Порт — номер процесу на хості», QUIC і 443/udp.

  1. Як запустити
  2. Що означає вивід
  3. На чому наголосити

Ідея за 2–3 хвилини: студенти відкривають YouTube і дивляться сокети власного браузера. Видно багато TCP-з'єднань на віддалений порт :443, кожне зі своїм локальним ефемерним портом. У Chrome є ще й UDP-сокети на :443: це QUIC, транспорт під HTTP/3. І все це належить одному процесу.

1. Як запустити

Що потрібно

  • macOS або Linux з lsof і python3 (на macOS обидва є). Docker потрібен лише для linux_check.sh.
  • Браузер з активними вкладками. За кілька секунд до запуску ввімкніть відео на YouTube у Chrome: простоюючі з'єднання закриваються за десятки секунд, і сокетів стане мало.
  • Docker-варіант потребує інтернету: linux_check.sh завантажує образ python:3.12-slim, через apt-get ставить lsof та iproute2 і відкриває з'єднання до 1.1.1.1:443.
  • Рядки lsof довгі, тому зробіть термінал широким або зменште шрифт. Решта виводу вміщується у звичайне вікно.
  • Перед парою один раз запустіть ./run_demo.sh саме на тому ноутбуці, що підключений до проєктора.

Одна команда (macOS / Linux)

cd 08-browser-ports
./run_demo.sh                  # IP анонімізовано: безпечно для проєктора
ANON=0 ./run_demo.sh           # справжні віддалені IP
LINES=25 ./run_demo.sh         # більше рядків lsof у кроці 2 (за замовчуванням 15)

Скрипт виконує чотири кроки:

  1. Запускає команду зі слайда як є (lsof -i -P -n | grep -iE 'chrome|safari'), рахує знайдені рядки і для порівняння рахує їх ще раз з +c 0.
  2. Показує виправлену команду: перші LINES рядків lsof +c 0 -i -P -n, відфільтровані за браузерами.
  3. Підсумок browser_ports.py за процесами: TCP → :443, UDP → :443 (QUIC), TCP → :80, інші порти й діапазон локальних портів.
  4. Діапазон ефемерних портів ядра (sysctl на macOS, /proc/sys/net/ipv4/ip_local_port_range на Linux).

Вручну, по кроках (наочніше для студентів)

# macOS: усі сокети браузера (+c 0 обов'язковий!)
lsof +c 0 -i -P -n | grep -iE 'chrom|safari|webkit|firefox|brave|edge|browser' | head -20

# лише QUIC: UDP на :443
lsof +c 0 -i -P -n | grep -iE 'chrom|webkit|firefox|brave|edge|browser' | grep UDP | grep ':443'

# діапазон ефемерних портів
sysctl net.inet.ip.portrange.first net.inet.ip.portrange.last

# скільки байтів пройшло через кожен UDP-сокет :443 (стовпці rxbytes / txbytes / pid)
netstat -anv -p udp | grep '\.443 '
# Linux
ss -tunp | grep ':443'               # t=TCP u=UDP n=числа p=процес
cat /proc/sys/net/ipv4/ip_local_port_range

Ключі lsof: -i мережеві сокети, -P порти числами (443, а не https), -n без зворотного DNS (значно швидше), +c 0 повна назва процесу.

Linux у Docker (для порівняння діапазонів)

Запускає контейнер demo08-linux. Браузера в ньому немає, тому python3 відкриває один TCP- і один UDP-сокет на 1.1.1.1:443, а скрипт друкує ip_local_port_range, lsof, ss -tunp і browser_ports.py --all.

Windows (не перевірено)

tasklist /FI "PID eq 1234"

У Windows UDP-ендпоінти не показують віддалену адресу, тож QUIC за «віддаленим портом 443» там не знайти. Простіше подивитися в браузері: DevTools → Network → правий клік по заголовку → увімкнути стовпець Protocol. h3 означає HTTP/3 через QUIC, h2 означає HTTP/2 через TCP.

2. Що означає вивід

Адреси анонімізовано. Нижче наведено реальний запис від 22.10.2026 (macOS 15, Chrome 155). Віддалені IP замінено на документаційні 203.0.113.x (RFC 5737), локальну адресу LAN на 192.168.0.x, ім'я користувача на <user>. Порти, PID, назви процесів, кількість сокетів і байтів справжні. Якщо студент спробує «пробити» ці IP: це не справжні сервери.

У ваших запусках усі числа будуть іншими: кількість сокетів, номери портів, PID. Під час запису YouTube не відкривали, тому на парі сокетів буде більше. Незмінною лишиться структура: сервер завжди на :443, а локальні порти завжди в діапазоні ОС.

Крок 1: команда зі слайда на macOS нічого не знаходить

=== 1. lsof -i -P -n | grep -iE 'chrome|safari'  (команда без +c 0) ===
знайдено рядків: 0                 ← COMMAND обрізано до «Google», «chrome» у ньому немає
з +c 0 (повна назва процесу): 21

На macOS lsof показує лише перші 9 символів назви процесу, а пробіли кодує як \x20. Тому Google Chrome Helper перетворюється на Google, а Safari на com.apple. Ключ +c 0 вмикає повну назву.

ПолеЗначення
COMMANDПроцес, якому належить сокет. У Chromium мережею займається окремий процес (network service), а не вікно браузера. На цьому Mac це Google Chrome Helper (Aperitif).
PIDНомер процесу. Усі ці сокети мають PID 745, тобто належать одному процесу.
USERЛогін власника. Анонімізація скрипта його не приховує (див. «Увага» нижче).
NODEПротокол транспортного рівня: TCP або UDP.
NAMEлокальна_адреса:порт->віддалена_адреса:порт. Ліворуч від стрілки ваша машина з ефемерним портом, який ядро вибрало під час connect(). Праворуч сервер із «відомим» портом 443.
(ESTABLISHED)Стан TCP-з'єднання в ядрі: рукостискання завершено. UDP-рядки стану не мають, бо в UDP немає з'єднання.
*:5353Сокет, що слухає на всіх адресах. Віддаленої адреси немає, бо це не з'єднання, а очікування пакетів.

Механізм. IP-адреса доставляє пакет до хоста. Порт доставляє його до сокета, а сокет належить процесу. Ядро знаходить сокет за п'ятіркою (протокол, локальний IP, локальний порт, віддалений IP, віддалений порт). Тому чотири з'єднання до 203.0.113.3:443 не плутаються: у кожного свій локальний порт.

UDP «зі стрілкою» (UDP ...:52189->...:443) означає під'єднаний (connected) UDP-сокет. Браузер викликав connect() на UDP-сокеті, і ядро лише запам'ятало адресу співрозмовника, жодного пакета при цьому не надіслано. Стан з'єднання QUIC живе всередині браузера, а не в ядрі.

1.1.1.1 є публічним DNS Cloudflare, а 172.17.0.6 є адресою контейнера, тож анонімізувати тут нічого. Recv-Q/Send-Q показують байти, що чекають у черзі прийому/відправлення (тут 0). Пастка: ss показує UDP як ESTAB, хоча з'єднання в UDP немає. Це лише означає, що на сокеті викликали connect() і адреса співрозмовника зафіксована. У скрипті TCP-сокет пройшов рукостискання, а UDP-сокет не надіслав жодного пакета.

3. На чому наголосити

Момент «ага!». «Той самий сервер, той самий порт 443, а з'єднань чотири. Як ядро знає, кому який пакет?» Відповідь у стовпці ліворуч від стрілки: локальні порти різні, і саме вони разом з адресами складають п'ятірку, за якою ядро знаходить сокет, а отже й процес.

Ключові тези

  1. Порт ідентифікує сокет процесу на хості. IP доводить пакет до машини, порт до процесу. Сервер завжди на :443, а клієнт отримує тимчасовий (ефемерний) порт.
  2. Ефемерні порти видає ядро з діапазону ОС: macOS 49152–65535 (перевірено), Linux 32768–60999 (перевірено в Docker), Windows 49152–65535 (за замовчуванням, тут не перевіряли), рекомендація IANA 49152–65535 (RFC 6335).
  3. 443/tcp і 443/udp — різні порти. Номери портів окремі для кожного протоколу. IANA закріпила обидва за HTTPS, і 443/udp використовується для HTTP/3.
  4. Чому QUIC працює поверх UDP. TCP живе в ядрах ОС, а NAT і файрволи розбирають і переписують його заголовки, тож новий транспортний протокол вони б просто відкидали. UDP проходить майже скрізь, тому QUIC використовує його як тонкий конверт, а надійність, порядок, контроль перевантаження і контроль потоку реалізує сам, у браузері.
  5. Переваги QUIC: немає блокування на початку черги (head-of-line blocking) між потоками; рукостискання разом із TLS 1.3 займає 1 RTT замість 2 (а при поновленні 0-RTT); з'єднання переживає зміну IP завдяки connection ID; майже весь заголовок зашифровано, тому Wireshark бачить лише «UDP 443».
  6. QUIC вмикається не одразу. Перший візит зазвичай іде по TCP (HTTP/2). Сервер повідомляє Alt-Svc: h3=":443", і браузер пробує QUIC. Якщо UDP/443 заблоковано, браузер мовчки лишається на TCP.

Запитання до аудиторії

ЗапитанняОчікувана відповідь
Який стовпець належить серверу, а який вам?Ліворуч від -> ви з ефемерним портом, праворуч сервер на 443.
Чому один процес має стільки сокетів?Різні джерела (сам сайт, CDN з відео, шрифти, аналітика) мають кожне своє з'єднання. HTTP/2 і HTTP/3 мультиплексують запити, тож це не «один сокет на запит».
UDP на 443? Хіба 443 не HTTPS по TCP?Порти окремі для кожного протоколу. 443/udp — це QUIC / HTTP/3.
Чому в UDP-рядках немає (ESTABLISHED)?Ядро не тримає стану з'єднання для UDP. Стан QUIC зберігається в браузері.
Порівняйте свій діапазон із сусідом.macOS/Windows починаються з 49152, Linux з 32768.
У кого нуль UDP :443? Чому?Файрвол чи VPN блокує UDP/443, або браузер не вибрав h3. Браузер тихо перейшов на TCP: саме тому QUIC проєктували із запасним варіантом.
Що таке :5353 і :5228?mDNS (пошук пристроїв у LAN) і push-канал Google. Порти позначають сервіси, а не лише «веб».

Швидкий експеримент: запустіть двічі з інтервалом 30 с. Ефемерні порти зміняться, бо з'єднання закриваються й відкриваються заново.

Які хибні уявлення виправляє демо

  • «Порт 443 означає TCP». Насправді є і 443/udp.
  • «Порт належить програмі назавжди». Клієнтський порт тимчасовий і щоразу інший.
  • «На один порт сервера можна мати лише одне з'єднання». З'єднання розрізняються за п'ятіркою, а не лише за портом сервера.
  • «ESTAB у ss для UDP означає з'єднання». Це лише під'єднаний сокет, і рукостискання не було.
  • «Мережею займається вікно браузера». У Chromium це окремий процес network service, а в Safari com.apple.WebKit.Networking.

Увага: виправте слайд. На macOS команда lsof -i -P -n | grep -iE 'chrome|safari' знаходить 0 рядків. Потрібна lsof +c 0 -i -P -n | grep -iE '...'. Перевірено на macOS 15, Chrome 155.

Увага: приватність на проєкторі. run_demo.sh за замовчуванням анонімізує віддалені IP, але стовпець USER показує ваш логін, а локальна адреса LAN лишається справжньою. Записаний expected_output.txt містить і логін, і адресу LAN: приберіть їх, перш ніж показувати файл. Сирі команди lsof показують справжні IP, тому краще пропускайте вивід через python3 browser_ports.py --anonymize --lines 20.

Увага: що не перевірено. Перевірено лише Chrome на macOS і Linux у Docker. Назви процесів інших браузерів (Edge, Brave, Arc, Firefox) і всі команди для Windows взято з документації, а не з тесту. Вкладки chrome://net-internals змінюються між версіями Chrome, тому перевірте їх на своїй версії заздалегідь.
