1. What the demo shows

A sender makes three calls in a row with no pause, each carrying one 100-byte message. The messages have visible edges: <MSG-1 ----…---- END-1>, so a merged or split chunk is easy to read.

  • UDP: 3 × sendto() → 3 × recvfrom(), each exactly 100 bytes. Boundaries survive.
  • TCP, merge: 3 × send() → one recv() of 300 bytes containing all three messages.
  • TCP, split: one sendall() of 1 MB → 2–3 recv() chunks of unpredictable sizes, even though the receiver asked for 1 MB per call.
  • The fix: a 4-byte length prefix before each message. The receiver gets the same 312-byte lump (or the same random 1 MB pieces) and still recovers exactly 3 (or 4) messages.
  • Bonus («відправив і забув»): the UDP sender run with no receiver at all reports success. No error, the datagrams just vanish.

Slides it supports: «UDP — відправив і забув» (no connection, no delivery guarantee, but each datagram is a self-contained unit) and the byte-stream point on the TCP slide (TCP delivers an ordered stream of bytes, not messages). It also answers the question students usually ask next: "so how does HTTP know where a request ends?" (line endings and Content-Length, i.e. framing).

2. The mechanism

UDP: one datagram in, one datagram out

Each sendto() builds exactly one UDP datagram (one IP packet, or a set of IP fragments that are reassembled before delivery). On the receiving host the kernel queues whole datagrams on the socket's receive queue, each with its own length and source address. recvfrom() always dequeues exactly one datagram. It never returns half of one, and never glues two together. If your buffer is smaller than the datagram, the rest is discarded, not saved for the next call. That is the price: UDP preserves boundaries, but if the queue is full or nobody is listening, the datagram is simply dropped. The sender is not told. On loopback, a closed port does trigger an ICMP "port unreachable", but an unconnected UDP socket never reports it to the application. That is why scenario 1b prints success.

TCP: a byte stream with sequence numbers, not messages

send() does not send a packet. It copies bytes into the socket's send buffer and returns. The TCP stack later cuts that buffer into segments according to MSS, the congestion and receive windows, and Nagle. Each byte has a sequence number. Nothing in the TCP header marks "a message ended here". The PSH flag is only a hint to deliver data promptly. It does not record where a message ends.

On the receiver, arriving segments are put in order and appended to the receive buffer, one contiguous run of bytes. recv(n) returns whatever is already there, up to n bytes, or blocks until at least 1 byte is available. So the size of a recv() result depends on timing: how much had arrived when the application asked. It does not depend on how the sender called send().

Why the 0.5 s sleep is honest

Without the sleep the result is a race between the sender and the receiving process waking up. On macOS we measured 100+200 in 9 of 10 runs and 100+100+100 once. On Linux it was 300 10 of 10. The sleep doesn't create the behaviour. It just picks one ordinary timing on purpose. Any real server that is busy for a moment (GC pause, slow disk, scheduler, a long-running request on the same thread) is in exactly this state. The point for students is that any of these results is legal TCP, and correct code must handle all of them. The tcpdump capture proves the sleep didn't change what went over the network. It still shows three separate 100-byte segments, each ACKed.

The opposite direction: one send, several recv()

A 1 MB sendall() is cut into segments (MSS on macOS lo0 is 16 332 bytes, as MTU 16 384 minus 52 bytes of headers; on Linux lo it's 65 483). The receiver is already blocked in recv(1000000). It wakes as soon as the first data lands and gets only what has arrived so far, e.g. 48 996 bytes = 3 × 16 332. The rest comes in later calls. A single recv() also can't return more than the receive buffer holds, so a message larger than the buffer (macOS auto-tunes up to 4 MB, Linux tcp_rmem max is usually 6 MB) can't arrive in one piece.

Nagle: merging can also happen at the sender

With Nagle on (the default, TCP_NODELAY=0), while sent data is still unacknowledged, the stack holds new small writes and sends them together when the ACK comes back. On loopback the ACK returns in microseconds, faster than Python can call send() again, so we saw no coalescing on loopback. With 50 ms of artificial delay (tc netem), Nagle merged sends 2 and 3 into one 200-byte segment. So the boundaries can be lost in two places, the sender (Nagle) and the receive buffer. Either way the receiver sees the same thing. sender.py sets TCP_NODELAY=1 by default so the wire shows clean 1:1 segments.

The fix: framing

Since TCP won't keep boundaries, the application protocol must encode them itself:

  • Delimiter: HTTP/1.x headers end each line with \r\n and the header block with an empty line. SMTP, Redis RESP and many text protocols work the same way.
  • Length prefix: HTTP Content-Length, HTTP/2 frames (24-bit length), TLS records (16-bit length), WebSocket frames, PostgreSQL and Kafka wire protocols.

receiver.py framed uses the standard loop. Append every recv() result to a buffer, then repeatedly take one whole frame (4-byte big-endian length + payload) while one is complete. If it isn't complete, wait for the next recv().

5. Things to point out or ask students

  • Before running scenario 2, ask: "Three sends of 100 bytes. How many recv calls, of what size?" Most will say 3 × 100. Then run it.
  • The UDP and TCP receivers sleep the same 0.5 s. Same timing, different result. The difference is the protocol, not the timing.
  • "Where did the boundaries disappear: in the network or in the receiver?" Show the capture. There were 3 segments, so it happened in the receive buffer. (Then: Nagle can also do it at the sender.)
  • "If I send 1 MB in one call, do I get 1 MB in one recv?" Scenario 3: no. So data = sock.recv(4096) followed by json.loads(data) is a bug that works on localhost and fails in production.
  • "How does a browser know where an HTTP response body ends?" Answer: Content-Length (length prefix), Transfer-Encoding: chunked (length-prefixed chunks), or closing the connection. Headers end at \r\n\r\n (delimiter).
  • "Then why not use UDP for everything?" Boundaries come at the cost of no delivery guarantee, no ordering, no flow control, and a size limit of about 64 KB per datagram (less in practice to avoid IP fragmentation). Show 1b again: «відправив і забув».
  • UTF-8 trap: a split can land in the middle of a multi-byte character. "ПРИВІТ" is 12 bytes, not 6, so decoding each recv() chunk separately can raise UnicodeDecodeError. Framing has to work on bytes, not characters.

6. Gotchas and what to do if it misbehaves live

  • Address already in use / port busy: a receiver from a previous run is still alive. lsof -nP -i :9116 -i :9106 then kill <pid>. Or use other ports: UDP_PORT=9206 TCP_PORT=9216 ./run_demo.sh.
  • "Порт 9116 закритий" from the sender: the receiver isn't running yet. Start the receiver first. run_demo.sh handles this itself.
  • UDP receiver shows only 2 datagrams (MSG-1 missing): the sender ran before the receiver had bound. That is UDP behaving correctly, and it makes a good live illustration. We hit this in Docker before adding the readiness wait. run_demo.sh now waits for «слухає».
  • Scenario 2 shows 100 + 200 instead of 300: only if you ran the receiver with --delay 0. With 0.5 s it was 300 in 20/20 runs across both OSes. If it ever happens, say "great, it just proved the point: sizes depend on timing" and rerun.
  • Scenario 3 comes back as one 1 000 000-byte chunk: not observed in 20 runs. With 200 KB it happened 2 of 10 times on macOS, which is why the default is 1 MB. If it happens, rerun or use --big-size 8000000, which is larger than the maximum receive buffer on both OSes, so it can't fit in one recv().
  • --rcvbuf does not make the split deterministic on macOS. It was tested and the window was already open, so it still sometimes delivered 200 KB in one piece. It's kept only for experiments.
  • Nagle on loopback: don't promise students they'll see coalescing with --nagle on plain loopback. On Linux it didn't happen in 6 of 6 runs. Use the NETEM=50ms run.
  • Python version: scripts are tested with macOS /usr/bin/python3 3.9 and Docker Python 3.12. No third-party packages.
  • Docker build needs internet (apt for tcpdump/iproute2). Build the image before class. docker rm -f demo06-run demo06-cap if a container name is stuck.
  • Interleaved output in manual mode: use two terminals. run_demo.sh prints the sender first, then the receiver, to avoid mixing.

7. 1-minute fallback

If nothing runs (no Python, firewall prompt, dead laptop), open expected_output.txt and show these lines in order:

  1. Section A, scenario 1: Разом recvfrom(): 3. UDP kept 3 messages.
  2. Section A, scenario 2: recv #1: 300 байтів … початки: <MSG-1, <MSG-2, <MSG-3. TCP merged them.
  3. Section C: сегментів з даними: 3. Three packets on the wire, yet one recv.
  4. Section A, scenario 3: 48996 + 951004. One send split into two.
  5. Section A, scenario 4: 312 байтів → 3 повідомлення. Framing fixes it, which is why HTTP has \r\n and Content-Length.
