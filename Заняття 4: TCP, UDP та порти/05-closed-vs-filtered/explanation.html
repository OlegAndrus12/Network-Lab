1. What the demo shows

A port scanner learns about a port only from what comes back after it sends a SYN. There are three possible outcomes, and they differ so much in time that you can tell them apart with time:

2. The mechanism: what the kernel does

Open: SYN → SYN-ACK

connect() makes the kernel send a SYN and put the socket in SYN_SENT. A socket in LISTEN on that port makes the server's kernel reply SYN-ACK; the client replies ACK and connect() returns. The application (open_server.py) is not even involved in the handshake: the kernel completes it and queues the connection for accept(). Time: one round trip.

Closed: SYN → RST,ACK

If no socket matches the destination port, TCP's rules (RFC 9293, "segment arrives in CLOSED state") say: answer with a reset. Because the SYN carried no ACK, the RST is sent with seq 0 and ack = their seq + 1, which tcpdump shows as Flags [R.]. The client kernel aborts the attempt and connect() fails with ECONNREFUSED ("Connection refused"). Time: also one round trip, so on loopback it is a fraction of a millisecond. A closed port is a definite, fast "no".

Filtered: SYN → silence → retransmits → timeout

If a firewall silently drops the SYN (or the address leads nowhere), nothing comes back. TCP cannot tell "lost packet" from "nobody there", so it does what it always does with unacknowledged data: retransmit on a timer. The initial retransmission timeout is 1 s (RFC 6298), and it grows with exponential backoff. The application just sits in connect() until either the kernel gives up or the application's own timeout fires.

Real SYN schedules we captured (seconds since the first SYN):
  • macOS 15.7, nc -G 20 to 10.255.255.1: 0, 1, 2, 3, 4, 5, 7, 11, 19. Five retransmits 1 s apart, then the gap doubles: 2, 4, 8. With no app timeout, macOS gives up after net.inet.tcp.keepinit = 75 000 ms, which is why plain nc -w 5 hung for 1:15.
  • Linux 6.12, default (tcp_syn_linear_timeouts=4): 0, 1.06, 2.08, 3.11, 4.13, 5.16, 7.20. Same shape: linear first, then doubling.
  • Linux 6.12, classic (tcp_syn_linear_timeouts=0): 0, 1.04, 3.09, 7.12. Gaps of 1, 2, 4 s: the textbook exponential backoff. Linux gives up after tcp_syn_retries=6 retransmits, about 127 s in total in the classic schedule.
So the "1 s, 2 s, 4 s…" from the textbook is the classic behaviour; both kernels on our machines now start with a few linear 1 s retries. Worth mentioning, because a student who captures this at home will see it.

Two more details in the macOS capture: the first SYN shows Flags [SEW] (it asks for ECN: E = ECE, W = CWR), and the retries are plain [S]. macOS drops the ECN request on retries, most likely as a fallback in case a middlebox discards ECN-flagged SYNs (our reading, not verified in the XNU source).

"Looks closed" on purpose: REJECT with tcp-reset

iptables -j REJECT --reject-with tcp-reset makes the firewall forge exactly the RST the kernel would send. On the wire it is identical ([R.], seq 0, ack = seq+1), so the scanner reports closed even though our listener on 9115 is running. DROP makes the same running service filtered. The admin chooses what the outside world sees.

Aside, not run in this demo: plain -j REJECT (the default icmp-port-unreachable) and a router sending ICMP "administratively prohibited" also give a fast answer. nmap reports ICMP-unreachable answers to a TCP probe as filtered. probe.py labels EHOSTUNREACH/ENETUNREACH as "filtered (ICMP/маршрут)", but we did not get such a reply on this network, so that branch is untested.

Why nc needs different flags

  • macOS /usr/bin/nc: -G 5 is the connect timeout. -w 5 is only an idle timeout after connecting and does not shorten connect(): we measured 1:15.01 for nc -vz -w 5 10.255.255.1 80.
  • Linux netcat-openbsd: -w 5 limits the connect too (real 8.010 s for -w 8).

3. Running it live

macOS (main path, about 30 s)

cd 05-closed-vs-filtered
./run_demo.sh                      # three "time nc" runs + probe table (+ tcpdump if allowed)

Or by hand, step by step, which is more dramatic for students:

python3 open_server.py &               # terminal 1: open port 9115
time nc -vz -G 5 127.0.0.1 9115        # open: instant "succeeded"
time nc -vz -G 5 127.0.0.1 9105        # closed: instant "Connection refused"
time nc -vz -G 5 10.255.255.1 80       # filtered: 5 s of silence, "Operation timed out"
python3 probe.py                       # the same as a table
lsof -nP -iTCP:9115 -sTCP:LISTEN       # who is listening (macOS netstat: netstat -an -p tcp | grep LISTEN)

tcpdump on macOS normally needs sudo. On this Mac it ran without sudo because the user is in the access_bpf group (installed by Wireshark's ChmodBPF). run_demo.sh detects this and skips capture otherwise. Manual capture:

sudo tcpdump -i lo0 -n -ttttt 'tcp port 9105 or tcp port 9115'
sudo tcpdump -i en0 -n -ttttt 'host 10.255.255.1'     # interface: route -n get 10.255.255.1

Docker / Linux lab (deterministic "filtered", about 30 s)

./run_demo.sh docker                       # build image demo05-lab, run the four sections
CLASSIC_BACKOFF=1 ./run_demo.sh docker     # same, SYN retries 1, 2, 4 s

Under the hood: docker run --rm --cap-add NET_ADMIN --name demo05-lab demo05-lab; CLASSIC_BACKOFF adds --sysctl net.ipv4.tcp_syn_linear_timeouts=0 (the sysctl is read-only from inside the container, so it has to be set at docker run). To drive it by hand, run docker run --rm -it --cap-add NET_ADMIN --name demo05-lab demo05-lab bash and then:

python3 open_server.py &
tcpdump -i lo -n -ttttt 'tcp port 9105' &
nc -vz -w 5 127.0.0.1 9105                                    # closed: RST
iptables -A INPUT -p tcp --dport 9105 -j DROP                 # now filtered
time nc -vz -w 8 127.0.0.1 9105                               # watch the SYN retries
iptables -F INPUT
iptables -A INPUT -p tcp --dport 9115 -j REJECT --reject-with tcp-reset
nc -vz -w 5 127.0.0.1 9115                                    # listener running, still "refused"
ss -ltn                                                       # Linux: who is listening

5. The UDP half: why UDP scanning is slow and ambiguous

UDP has no handshake. A probe datagram can produce:

  • Closed: the kernel replies with ICMP type 3 code 3, "port unreachable". A connected UDP socket receives that as ECONNREFUSED on the next recv(), so probe.py --udp sees it instantly.
  • Open: the datagram is delivered to the application, which usually ignores a payload it does not understand. Silence.
  • Filtered: dropped. Silence.

Open and filtered both look like silence, so nmap reports open|filtered, and the scanner has to wait for a timeout (and retry, since UDP packets get lost) on every such port. Kernels also rate-limit ICMP errors (Linux: net.ipv4.icmp_ratelimit / icmp_msgs_per_sec), so even closed ports can answer slowly in bulk. nmap works around this by sending protocol-specific payloads (a real DNS query to 53, etc.) to provoke a reply from open services.

nc lies about UDP, and differently per OS. On macOS, nc -vzu 127.0.0.1 9105 printed "succeeded!" with exit code 0 for the closed port, even though tcpdump showed the ICMP port-unreachable replies. On Linux (netcat-openbsd), the same command printed nothing and exited 1, while the open port printed "succeeded" after the 2 s timeout. "Succeeded" for UDP only means "no error arrived (in time)". A nice live moment, if you have time.

6. Points to make and questions for students

  • Ask before running: "Which will be faster, the closed port or the firewalled one? Why?" Then show the 0.1 ms vs 5 s.
  • Closed is not "worse" than open from a scanner's point of view: it proves the host is alive and reachable. That is why admins prefer DROP on the perimeter.
  • Why does a scanner love closed ports? One RTT per port, no ambiguity. Why does it hate filtered? It must wait out a timeout per port, so scanners send many probes in parallel.
  • Show that DROP hides even a running service, and REJECT tcp-reset makes it look closed. "Can a scanner ever be sure a port is closed?" (No: it only knows what came back.)
  • Why does the SYN carry the same seq on every retry? (It is the same connection attempt being retransmitted, not a new one.)
  • UDP: "If the open port is silent and the firewalled port is silent, how could nmap tell them apart?" (Send a valid request for the expected service and hope for an answer.)

7. Gotchas and what to do if it misbehaves

  • Filtered case is instant instead of 5 s. The classroom network probably answered with ICMP unreachable or a router RST, or there is no default route. Check route -n get 10.255.255.1 (macOS) / ip route get 10.255.255.1 (Linux). Try FILTERED_HOST=192.0.2.1 ./run_demo.sh (TEST-NET-1, not routed on the internet; untested here) or go straight to the Docker lab, which is fully deterministic.
  • VPN / corporate network. If the route goes through utun*, the VPN may route 10.0.0.0/8 to a real network. run_demo.sh prints a warning in that case. Disconnect the VPN or use Docker.
  • "Порт 9115 уже хтось слухає". A previous open_server.py is still alive. lsof -nP -iTCP:9115 -sTCP:LISTEN, then kill <PID>. (If you start it by hand with &, stop it with kill %1.)
  • nc hangs for 75 s on macOS. You used -w. Use -G 5. Ctrl+C is safe.
  • No tcpdump output on macOS. It needs sudo unless you are in the access_bpf group; the demo works without the capture.
  • Docker: iptables error. The container needs --cap-add NET_ADMIN (run_demo.sh adds it). CLASSIC_BACKOFF=1 fails on kernels without tcp_syn_linear_timeouts; just drop the variable.
  • First Docker run is slow (image build, apt-get). Run ./run_demo.sh docker once before class so the image is cached; later runs take about 30 s.
  • Leftovers. The container uses --rm; check with docker ps -a --filter name=demo05. Remove the image after the course with docker rmi demo05-lab.

8. 1-minute fallback

If the network or Docker misbehaves, open expected_output.txt and show:

  1. Section A: the three time nc results and the table (0.10 ms vs 5.00 s).
  2. Section C: the 1:15 hang of nc -w 5 on macOS, a nice "read the man page" moment.
  3. Section E, part 2 and 3: SYN retries under DROP vs the forged RST under REJECT, with the listener running in both.
  4. Section F: the classic 1, 2, 4 s backoff.
  5. Section D/E part 4: UDP closed = ICMP, open = filtered = silence.

Summary line for the slide: TCP always answers (SYN-ACK or RST) unless someone drops the packet, so every port is open, closed or "suspiciously silent" after one round trip. UDP answers only when the port is closed, so silence is ambiguous and every silent port costs a full timeout.
