Демо 05: закритий порт проти відфільтрованого

Тема 4 (TCP, UDP та порти), слайд «Чому TCP сканувати легко…». Порти: 9115 (відкритий), 9105 (закритий). Усі цифри нижче взяті з expected_output.txt (реальні запуски 22.10.2026: macOS 15.7 і Linux 6.12 у Docker Desktop).

Суть за 10 секунд Сканер дізнається про порт лише з того, що повернулося у відповідь на SYN. Відкритий порт відповідає SYN-ACK, закритий RST, обидва за долі мілісекунди. Порт за фаєрволом мовчить, і клієнт чекає до тайм-ауту. Тому стану відрізняються секундоміром.

1. Як запустити

Що потрібно

  • python3 і nc (на macOS вбудований, на Linux потрібен netcat-openbsd).
  • Вільні порти 9105 і 9115 на 127.0.0.1 (скрипт перевіряє сам).
  • Мережа, де 10.255.255.1 маршрутизується і ніхто не відповідає (звичайна домашня мережа без VPN підходить).
  • tcpdump необов'язковий: run_demo.sh запускає його лише без пароля (root або macOS із групою access_bpf, яку ставить ChmodBPF від Wireshark). Інакше пише «tcpdump пропущено» і працює далі.
  • Для Linux-лабораторії: Docker. Перша збірка образу потребує інтернету (apt-get) і йде повільно, тому запустіть ./run_demo.sh docker один раз до заняття. Далі близько 30 с.

Однією командою (macOS або Linux, близько 30 с)

cd 05-closed-vs-filtered
./run_demo.sh

Три запуски time nc (open, closed, filtered), потім таблиця від probe.py, потім tcpdump (якщо дозволено). Скрипт сам підбирає ключ тайм-ауту: -G на macOS, -w на Linux.

Linux-лабораторія в Docker (детерміновано, близько 30 с)

./run_demo.sh docker                       # збирає образ demo05-lab і проганяє 4 розділи
CLASSIC_BACKOFF=1 ./run_demo.sh docker     # те саме, але SYN-повтори 1, 2, 4 с

Усередині: docker run --rm --cap-add NET_ADMIN --name demo05-lab demo05-lab. CLASSIC_BACKOFF додає --sysctl net.ipv4.tcp_syn_linear_timeouts=0 (з контейнера цей sysctl змінити не можна, тому лише при docker run).

Вручну, крок за кроком (наочніше для студентів)

macOS, два термінали:

python3 open_server.py                    # термінал 1: слухач на 9115

time nc -vz -G 5 127.0.0.1 9115           # термінал 2: open, миттєво "succeeded"
time nc -vz -G 5 127.0.0.1 9105           # closed, миттєво "Connection refused"
time nc -vz -G 5 10.255.255.1 80          # filtered, 5 с тиші, "Operation timed out"
python3 probe.py                          # те саме таблицею (цілі за замовчуванням)
lsof -nP -iTCP:9115 -sTCP:LISTEN          # хто слухає порт

Захоплення на macOS (потрібен sudo, якщо ви не в access_bpf):

sudo tcpdump -i lo0 -n -ttttt 'tcp port 9105 or tcp port 9115'
sudo tcpdump -i en0 -n -ttttt 'host 10.255.255.1'   # інтерфейс: route -n get 10.255.255.1

Docker вручну (образ уже зібрано через ./run_demo.sh docker):

docker run --rm -it --cap-add NET_ADMIN --name demo05-lab demo05-lab bash

python3 open_server.py &
tcpdump -i lo -n -ttttt 'tcp port 9105' &
nc -vz -w 5 127.0.0.1 9105                                   # closed: RST
iptables -A INPUT -p tcp --dport 9105 -j DROP                # тепер filtered
time nc -vz -w 8 127.0.0.1 9105                              # дивимось повтори SYN
iptables -F INPUT
iptables -A INPUT -p tcp --dport 9115 -j REJECT --reject-with tcp-reset
nc -vz -w 5 127.0.0.1 9115                                   # слухач працює, а "refused"
ss -ltn                                                      # хто слухає (Linux)

Якщо щось пішло не так

  • Filtered відповідає миттєво, а не за 5 с. Мережа аудиторії повернула ICMP unreachable чи RST або немає маршруту за замовчуванням. Перевірте route -n get 10.255.255.1 (macOS) / ip route get 10.255.255.1 (Linux). Спробуйте FILTERED_HOST=192.0.2.1 ./run_demo.sh (TEST-NET-1; не перевірено) або одразу Docker: там усе детерміновано.
  • VPN / корпоративна мережа. Якщо маршрут іде через utun*, скрипт надрукує «УВАГА: маршрут іде через VPN». Вимкніть VPN або беріть Docker.
  • «Порт 9115 уже хтось слухає». Живий попередній open_server.py: lsof -nP -iTCP:9115 -sTCP:LISTEN, потім kill <PID> (або kill %1, якщо запускали з &).
  • nc на macOS висить 75 с. Ви використали -w. Потрібно -G 5. Ctrl+C безпечний.
  • Немає виводу tcpdump на macOS. Потрібен sudo; демо працює і без захоплення.
  • Docker: помилка iptables. Потрібен --cap-add NET_ADMIN (run_demo.sh додає). Якщо падає CLASSIC_BACKOFF=1, ядро не має tcp_syn_linear_timeouts: запускайте без змінної.
  • Залишки. Контейнер з --rm; перевірка: docker ps -a --filter name=demo05. Після курсу: docker rmi demo05-lab.
Запасний план на 1 хвилину Відкрийте expected_output.txt: розділ A (три time nc і таблиця), C (пастка -w, 1:15), E частини 2–3 (DROP проти REJECT при працюючому слухачі), F (backoff 1, 2, 4 с), D / E частина 4 (UDP).

2. Що означає вивід

macOS, ./run_demo.sh (розділ A)

Маршрут до 10.255.255.1: інтерфейс en0     ← маршрут є, через Wi-Fi, не VPN

$ time nc -vz -G 5 127.0.0.1 9115
Connection to 127.0.0.1 port 9115 [tcp/*] succeeded!
real 0.019 s                                ← open: SYN → SYN-ACK → ACK

$ time nc -vz -G 5 127.0.0.1 9105
nc: connectx to 127.0.0.1 port 9105 (tcp) failed: Connection refused
real 0.008 s                                ← closed: так само швидко, але «ні»

$ time nc -vz -G 5 10.255.255.1 80
nc: connectx to 10.255.255.1 port 80 (tcp) failed: Operation timed out
real 5.010 s                                ← filtered: дочекались нашого тайм-ауту
  • -v друкує результат, -z лише перевіряє з'єднання без даних, -G 5 тайм-аут connect() на macOS.
  • 8–19 мс у nc це здебільшого запуск процесу. Сам connect() міряє probe.py:
ціль                | результат                      | час     | термін nmap
--------------------+--------------------------------+---------+------------
127.0.0.1:9115/tcp  | SYN-ACK: з'єднання встановлено | 0.17 мс | open
127.0.0.1:9105/tcp  | RST: Connection refused        | 0.10 мс | closed
10.255.255.1:80/tcp | тиша, тайм-аут 5 с             | 5.00 с  | filtered
  • результат: що повернуло ядро. Успішний connect() = прийшов SYN-ACK; ConnectionRefusedError = прийшов RST; socket.timeout = не прийшло нічого.
  • термін nmap: як цей стан називає сканер. Різниця 0.10 мс проти 5.00 с, тобто у 50 000 разів.
  • Мілісекунди змінюються від запуску до запуску; 5.00 с завжди дорівнює тайм-ауту.

tcpdump: що реально летить

# lo0, закритий порт
 00:00:00.017497 IP 127.0.0.1.58920 > 127.0.0.1.9105: Flags [S], seq 265015013, win 65535, length 0
 00:00:00.017510 IP 127.0.0.1.9105 > 127.0.0.1.58920: Flags [R.], seq 0, ack 265015014, win 0, length 0
                                                    ↑ RST,ACK через 13 мкс; ack = їхній seq + 1
  • -ttttt: час від першого пакета, тож видно паузи. [S] = SYN, [S.] = SYN-ACK, [R.] = RST+ACK, [.] = ACK.
  • Відповідає ядро, не програма: на порту немає сокета в стані LISTEN, і за правилами TCP (RFC 9293) на такий SYN ядро шле скидання. Оскільки в SYN не було ACK, RST має seq 0 і ack = seq + 1.
  • Для відкритого порту так само відповідає ядро: рукостискання завершується ще до accept() у open_server.py.
# en0, 10.255.255.1, окремий запуск nc -G 20 (розділ B)
 00:00:00.000000 IP 192.168.0.155.58861 > 10.255.255.1.80: Flags [SEW], seq 1128311429, ...  ← SYN з запитом ECN
 00:00:01.000325 IP 192.168.0.155.58861 > 10.255.255.1.80: Flags [S], seq 1128311429, ...    ← той самий seq: повтор
 00:00:02.000073 ...   00:00:03.000201 ...   00:00:03.999641 ...   00:00:05.000018 ...          ← щосекунди
 00:00:07.000574 IP 192.168.0.155.58861 > 10.255.255.1.80: Flags [S], ...                    ← пауза 2 с
 00:00:11.000815 IP 192.168.0.155.58861 > 10.255.255.1.80: Flags [S], ...                    ← пауза 4 с
 00:00:19.001199 IP 192.168.0.155.58861 > 10.255.255.1.80: Flags [S], ...                    ← пауза 8 с; жодної відповіді
  • TCP не відрізняє «пакет загубився» від «там нікого немає», тому робить те, що завжди: повторює за таймером з експоненційним backoff.
  • macOS: 5 повторів через 1 с, далі паузи подвоюються (2, 4, 8). Без тайм-ауту програми macOS здається через net.inet.tcp.keepinit = 75 000 мс.
  • [SEW]: перший SYN просить ECN (E = ECE, W = CWR); повтори вже звичайні [S]. Ймовірно, обхід посередників, що відкидають SYN з ECN (наше припущення, у коді XNU не перевірено).

127.0.0.1:9105/udp | тиша, тайм-аут 2 с    | 2.00 с  | open|filtered   ← те саме, що й відкритий
  • У UDP немає рукостискання. Закритий порт: ядро шле ICMP type 3 code 3 «port unreachable», і «підключений» UDP-сокет отримує його як ECONNREFUSED на recv().
  • Відкритий порт отримує датаграму, але програма мовчить (так поводиться більшість сервісів на незрозумілий запит). Відфільтрований теж мовчить. Тому nmap пише open|filtered і чекає тайм-аут на кожному такому порту.
  • На macOS (розділ D) та сама таблиця: 0.30 мс / 2.00 с.

3. На чому наголосити

Момент «ага» Закритий порт відповідає так само швидко, як відкритий (0.10 мс проти 0.17 мс), а порт за фаєрволом коштує повний тайм-аут (5.00 с). Стан порту видно секундоміром, без жодного сканера.

Ключові тези

  1. Сканер знає лише те, що повернулося. SYN-ACK = open, RST = closed, тиша = filtered. Більше інформації немає.
  2. Відповідає ядро, а не програма. І SYN-ACK, і RST шле ядро; програма навіть не бере участі в рукостисканні.
  3. Тиша = ретрансмісії. Без відповіді TCP повторює SYN з тим самим seq і зростаючими паузами. Підручникові 1, 2, 4 с це класика; сучасні macOS і Linux спершу роблять кілька повторів через 1 с.
  4. Адмін обирає, що бачить світ. DROP ховає навіть працюючий сервіс (filtered), REJECT tcp-reset робить його схожим на closed.
  5. UDP сканувати важко. Відповідає лише закритий порт; відкритий і відфільтрований однаково мовчать, і кожен такий порт коштує тайм-аут.

Питання до аудиторії

До запуску: що буде швидше, закритий порт чи порт за фаєрволом? Чому?
Закритий: ядро одразу відповідає RST. За фаєрволом відповіді немає, клієнт чекає тайм-аут.
Чому сканер «любить» закриті порти?
Один RTT на порт, жодної двозначності, і це доводить, що хост живий. Тому на периметрі адміни віддають перевагу DROP.
Чому в усіх повторах SYN той самий seq?
Це ретрансмісія тієї самої спроби з'єднання, а не нове з'єднання.
Чи може сканер бути певним, що порт закритий?
Ні: REJECT tcp-reset підробляє RST, а слухач при цьому працює. Сканер знає лише, що прийшло.
UDP: відкритий порт мовчить і відфільтрований мовчить. Як nmap їх розрізняє?
Надсилає справжній запит очікуваного сервісу (наприклад, DNS-запит на 53) і сподівається на відповідь.

Які хибні уявлення виправляє демо

  • «Закритий порт = порт за фаєрволом». Ні: закритий відповідає RST, фаєрвол (DROP) мовчить.
  • «Filtered означає, що пакет не дійшов». tcpdump у Docker бачить кожен SYN; просто ніхто не відповідає.
  • «Повтори SYN завжди 1, 2, 4 с». На наших ядрах спершу йдуть лінійні повтори по 1 с (див. розділи B і E проти F).
  • «nc написав succeeded, отже UDP-порт відкритий». Для UDP це означає лише «ICMP-помилки не прийшло вчасно».

Застереження з тестування

macOS: -w не обмежує connect() time nc -vz -w 5 10.255.255.1 80 на macOS висів 1:15.01 (розділ C). На macOS потрібно -G 5. На Linux (netcat-openbsd) -w обмежує і connect(). Якщо на слайді -w без уточнення ОС, виправте.
nc -u бреше, і по-різному на різних ОС macOS: nc -vzu 127.0.0.1 9105 надрукував «succeeded!» з кодом 0 для закритого порту, хоча tcpdump показав ICMP port unreachable. Linux: той самий виклик нічого не надрукував і вийшов з кодом 1, а відкритий порт дав «succeeded» лише після тайм-ауту 2 с. Гарний живий момент, якщо є час.
Особисті дані у виводі expected_output.txt (розділи A і B) містить домашню адресу 192.168.0.155. Якщо проєктуєте файл, приберіть її або покажіть лише Docker-розділи.
Не перевірено FILTERED_HOST=192.0.2.1; гілка probe.py «filtered (ICMP/маршрут)» (ICMP unreachable від маршрутизатора в нашій мережі не трапився); простий -j REJECT з ICMP за замовчуванням не запускали.
Підсумок для слайда TCP завжди відповідає (SYN-ACK або RST), якщо пакет ніхто не відкидає, тому кожен порт за один RTT стає open, closed або «підозріло тихим». UDP відповідає лише тоді, коли порт закритий, тож тиша двозначна і кожен тихий порт коштує повний тайм-аут.
