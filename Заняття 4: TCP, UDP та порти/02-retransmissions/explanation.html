1. What the demo shows

A Linux container adds 5% random packet loss (and 5 ms delay each way) to its loopback interface with tc netem. curl downloads a 2 MB file from python3 -m http.server 9102 while tcpdump records a .pcap. You open the pcap in Wireshark on the Mac, and Wireshark itself labels and colours the loss-recovery events:

  • TCP Previous segment not captured: a hole in the sequence numbers (a segment was lost).
  • TCP Dup ACK #1/#2/#3…: the receiver keeps repeating the same ack number.
  • TCP Fast Retransmission: loss detection method 1, the sender reacts to duplicate ACKs.
  • TCP Retransmission after a pause of about 0.2 s or more: loss detection method 2, the retransmission timer (RTO) fired.

Those are exactly the two ways of noticing a loss on the slide: duplicate ACKs (fast, about 1 RTT) and timeout (slow, at least 200 ms on Linux). Analyze → Expert Information counts all of them. The kernel's own counters (nstat) are printed alongside, so you can check Wireshark's labels against what TCP actually did.

2. The mechanism

2.1 Where the loss happens and what tcpdump can see

tc qdisc add dev lo root netem delay 5ms loss 5% installs a queueing discipline on the egress side of lo. On loopback every packet, in both directions, leaves through that egress, so data segments and ACKs are both dropped at 5%. Each direction gets 5 ms of delay, so RTT is about 12 ms (in the sample the SYN-ACK arrives 6.1 ms after the SYN).

tcpdump taps the packet after the qdisc, just before it is handed to the receiving side. So a dropped packet never appears in the capture. The pcap shows the receiver's view: you never see a lost segment, only the hole it leaves behind (Previous segment not captured) and then the retransmission. Because of the delay, the timestamps are effectively arrival times: a retransmission appears about 6 ms after the dup ACK that triggered it.

2.2 Why MTU 1500 and the offload settings

Loopback's default MTU is 65536, so the MSS is 65483 bytes. A 2 MB file is then only about 32 data segments. With 5% loss that is one or two events in total (real run with MTU=65536: 73 frames, 1 fast retransmission, 1 RTO). That is too sparse to teach from. With MTU 1500 the MSS is 1448 bytes (1460 minus 12 bytes of TCP timestamps), about 1450 data segments and dozens of events, the same as on a real Ethernet path.

Two more settings in inside.sh make the loss behave like "5% of segments, independently":

  • ethtool -K lo tso off gso off gro off. Without this the kernel builds 64 KB "super-segments" and tcpdump records those instead of 1448-byte segments.
  • ip link set lo gso_max_segs 1. Even with the offloads off, Linux TCP still puts several MSS into one buffer (skb) and splits it in software after the qdisc. netem drops whole buffers, so losses came in bursts. In a test run before this fix one drop removed 21 consecutive segments. With gso_max_segs 1 the hole sizes in a real run were 65 single-segment holes and one two-segment hole.

This is a nice aside if students ask why a "5% random" loss can wipe out a whole burst: the loss happens per buffer, not per packet.

2.3 Method 1: duplicate ACKs and fast retransmit

TCP ACKs are cumulative: "I have everything up to byte N, send N next". When a segment is lost, each later segment that arrives makes the receiver send the same ack number again. Those are duplicate ACKs. Classic TCP (RFC 5681) treats the third duplicate ACK as proof of loss rather than reordering, retransmits the missing segment at once without waiting for a timer, and halves the congestion window. That is fast retransmit, which recovers in about one RTT.

Modern Linux is not literally "3 dup ACKs". With SACK it counts how much data the receiver reports beyond the hole (RFC 6675) and uses time-based RACK (RFC 8985). In the real captures you will see both cases:

  • the retransmission comes before Dup ACK #3, because one SACK block already shows several segments received past the hole (live run, frame 112 after Dup ACK #2);
  • Wireshark shows Dup ACK #4…#18 before the retransmission (sample_nosack.pcap, frames 187–216). The sender had decided earlier, but those duplicate ACKs were already in flight (half an RTT), and the retransmission needs another 6 ms to reach the capture point.

For the slide, "3 duplicate ACKs" is the right rule to teach. Just don't promise students the retransmission will sit exactly after #3.

2.4 Method 2: the retransmission timeout (RTO)

Each sender keeps a timer for the oldest unacknowledged segment. RTO = SRTT + 4·RTTVAR (RFC 6298), clamped to a minimum. RFC 6298 recommends a 1 s minimum; Linux uses 200 ms. On a 12 ms RTT path the RTO is therefore essentially 200 ms plus a little. In every real run the RTO retransmissions came after a gap of 0.21–0.29 s since the previous packet of the connection (more than 0.2 s when the RTO had already backed off). If the timer fires, the sender assumes the network is badly congested: cwnd goes to 1 segment, slow start begins again, and the RTO doubles on each repeat (exponential backoff).

The timer is the fallback when duplicate ACKs cannot work:

  • the retransmission itself is lost (the live run below: frame 169 is a fast retransmission of seq 140663, it is dropped too, and frame 170 resends it 220 ms later);
  • a loss at the tail of a burst, with no later segments to produce dup ACKs (Linux first sends a Tail Loss Probe, counted as TcpExtTCPLossProbes; the RTO fires if that also fails);
  • all ACKs for a flight are lost. In sample_sack.pcap, frames 103–104 deliver seq 79847 and 81295, but both ACKs are dropped. Frame 105 is an RTO retransmission of seq 79847 at +0.244 s, and the next ACK (frame 106) carries a D-SACK for exactly 79847–81295. D-SACK means "I already had this": the data had arrived and the RTO was spurious, caused by lost ACKs. Wireshark shows this as the Warn "D-SACK Sequence". Frames 109–111 repeat the pattern, this time with a +0.288 s gap.

Wireshark's "TCP Retransmission" does not always mean RTO. Wireshark labels any re-sent sequence number that was not preceded by dup ACKs as "Retransmission", including TLP probes and RACK retransmissions. To find real timeouts, look for a ≥0.2 s gap: tcp.analysis.retransmission && !tcp.analysis.fast_retransmission && tcp.time_delta >= 0.2. In the sample this matches 3 frames, and the kernel counted TcpExtTCPTimeouts 3. In the 5% test runs the two numbers agreed, apart from one run where a lost SYN was counted by the kernel. At 10% loss Wireshark found slightly fewer (14 vs 16, 12 vs 15), because an RTO retransmission that is itself dropped never reaches the capture.

2.5 What SACK changes

Both ends announce SACK_PERM in the SYN/SYN-ACK. After that, every duplicate ACK carries up to 3–4 SACK blocks (shown by Wireshark as SLE=… SRE=…): "I'm missing byte N, but I already have these ranges after it". The sender builds a scoreboard and can resend every hole in one RTT, sending only what is missing. Without SACK (NewReno) the sender learns about one hole per RTT, and a second loss in the same window often ends in a timeout.

2.6 Why the counts don't match exactly

The kernel says TcpRetransSegs 70, while Wireshark labels 34 + 14 + 16 = 64 frames (fast + other + out-of-order, Wireshark 4.6.9). The difference is retransmissions that were themselves dropped by netem and so never captured. Wireshark's labels are heuristics computed from the trace, not flags inside the packets. A retransmission that arrives very soon after the hole is often labelled Out-Of-Order, and the split between "Retransmission" and "Out-Of-Order" differs between Wireshark versions: 4.4.19 in the container labels 7 and 23, while 4.6.9 on the Mac labels 14 and 16 for the same pcap. Dup ACK, Fast Retransmission and the ≥0.2 s RTO counts are the same in both versions.

3. Running it live

Before class (needs internet, about 1–2 min): cd ports/02-retransmissions && ./run_demo.sh once. This builds the image demo02-retrans. In class it then takes about 10 s and needs no network. Install Wireshark if needed: brew install --cask wireshark (it is already in /Applications on this Mac). Opening a pcap file needs no sudo.

Option A: one command (macOS or Linux, Docker only, no sudo)

cd ports/02-retransmissions
./run_demo.sh                      # 5% loss, 2 MB, SACK on   -> capture.pcap
open -a Wireshark capture.pcap     # macOS   (Linux: wireshark capture.pcap &)

# variants
LOSS=10% ./run_demo.sh             # many RTOs, guaranteed
SACK=0 PCAP=nosack.pcap ./run_demo.sh
MTU=65536 PCAP=bigmtu.pcap ./run_demo.sh   # show why we lowered the MTU

The container has its own network namespace, so tc, MTU and offload changes affect only the container's lo and disappear with it (--rm). The folder is mounted at /demo, so capture.pcap lands straight in the folder. No docker cp is needed.

Option B: step by step, in front of students (Docker)

# terminal 1: start a long-running container and break its loopback
docker run -d --rm --name demo02-live --cap-add NET_ADMIN -v "$PWD":/demo demo02-retrans sleep infinity
docker exec demo02-live bash -c '
  ip link set lo mtu 1500
  ethtool -K lo tso off gso off gro off
  ip link set lo gso_max_segs 1
  tc qdisc add dev lo root netem delay 5ms loss 5%
  tc qdisc show dev lo
  mkdir -p /srv && head -c 2M /dev/urandom > /srv/file.bin'
docker exec -d demo02-live python3 -m http.server 9102 --bind 127.0.0.1 --directory /srv
docker exec -d demo02-live tcpdump -i lo -n -U -w /demo/live.pcap 'tcp port 9102'

# terminal 2: live "Wireshark labels" in the terminal, only the interesting frames
docker exec -it demo02-live tshark -l -i lo -f 'tcp port 9102' \
    -Y 'tcp.analysis.flags && !tcp.analysis.window_update'

# terminal 1: the download (watch the progress bar stall during RTOs)
docker exec demo02-live curl -o /dev/null http://127.0.0.1:9102/file.bin
docker exec demo02-live nstat -z TcpRetransSegs TcpExtTCPFastRetrans TcpExtTCPTimeouts

# finish: stop the capture, open it, clean up
docker exec demo02-live pkill tcpdump
open -a Wireshark live.pcap
docker rm -f demo02-live

This exact sequence was run while preparing the demo. Without the -v mount, use docker cp demo02-live:/tmp/live.pcap . instead.

Option C: a real Linux machine with sudo (not run here)

These are the same commands as inside.sh, but on the host's own lo. They were not tested on a bare Linux host (none was available). They change system-wide loopback behaviour, so undo them afterwards.

What is different on macOS

  • There is no tc/netem. The macOS equivalent is dummynet (dnctl + pfctl) or Apple's Network Link Conditioner. Both need sudo, so they were not tested, which is why the demo uses Docker.
  • Docker Desktop runs containers in a Linux VM (kernel 6.12.76-linuxkit here). The TCP you see is Linux TCP, not the macOS stack.
  • netstat -s -p tcp on this Mac printed only zeros without sudo (e.g. 0 data packet (0 byte) retransmitted, 0 retransmit timeout). Use nstat in the container for counters.
  • The analysis runs on the Mac too: python3 analyze.py sample_sack.pcap uses the tshark in Wireshark.app (verified with 4.6.9).

In Wireshark

  • The coloring rule "Bad TCP" (black background, red text) highlights all of the events. Dup ACKs and retransmissions stand out immediately when you scroll.
  • Analyze → Expert Information: expand Warnings (Previous segment not captured, Out-Of-Order, D-SACK) and Notes (Duplicate ACK #n, fast retransmission, retransmission). Double-clicking an entry jumps to the packet.
  • Useful column: right-click a field → Apply as Column on tcp.time_delta (enable Protocol Preferences → TCP → Calculate conversation timestamps) to make the 0.2 s RTO gaps visible.
  • If the Info column says "Continuation", that is the HTTP dissector. Analyze → Enabled Protocols → uncheck HTTP shows Seq/Ack/Len instead (analyze.py does the same with --disable-protocol http).
  • Optional: Statistics → TCP Stream Graphs → tcptrace on a server→client packet shows retransmissions and SACK ranges graphically. I did not check this view, since there is no GUI in this environment.

5. Things to point out and ask students

  • "Who notices the loss first, the sender or the receiver?" The receiver, from the sequence gap. But only the sender can fix it, and it learns about the loss through ACKs.
  • "Why wait for 3 duplicate ACKs, not 1?" Packets can be reordered. One or two duplicates may just mean "a bit late". Three is the classic threshold that trades speed against false alarms.
  • "Why is fast retransmit 'fast'?" Compare the gaps: about 6–12 ms (one RTT) against at least 200 ms for the RTO. Ask them to find a gap in tcp.time_delta.
  • "When can't dup ACKs help?" The last segment is lost, the retransmission is lost (live run, frame 169→170), or all ACKs are lost (sample, frame 105). Then only the timer is left.
  • "What does SLE/SRE tell the sender that Ack alone can't?" Which ranges after the hole arrived, so more than one hole can be repaired per RTT. Compare RTO counts with and without SACK.
  • "5% loss, so why did the download become about 15× slower (0.36 s → 5.4 s)?" Every loss halves cwnd and every RTO resets it to 1 segment. Loss tells TCP to slow down (congestion control), and that costs far more than the bytes resent.
  • "Is every 'TCP Retransmission' a timeout?" No: Wireshark guesses. Check with the time gap and the kernel counter.
  • Exercise 3: give students sample_sack.pcap and ask for the counts of dup ACKs, fast retransmissions and RTOs using the filters in section 3. The expected answers are in the filter table above (Wireshark 4.6.9).

7. One-minute fallback

  1. open -a Wireshark ports/02-retransmissions/sample_sack.pcap (the committed real capture, no Docker needed).
  2. Filter frame.number <= 27 to show the hole, Dup ACK #1…#7 with growing SACK blocks, and the fast retransmission (section 4.2).
  3. Filter frame.number >= 102 && frame.number <= 111 to show two RTOs at +0.244 s and +0.288 s, each followed by a D-SACK (section 4.3). All 3 RTOs: tcp.analysis.retransmission && !tcp.analysis.fast_retransmission && tcp.time_delta >= 0.2 (enable conversation timestamps).
  4. Analyze → Expert Information for the totals.
  5. No Wireshark at all: show expected_output.txt section A (terminal output) and E (live tshark, frames 169→170).
