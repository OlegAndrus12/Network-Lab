Демо 2. Повторні передачі у Wireshark

Тема 4 (TCP, UDP та порти). Слайд «Два способи помітити втрату», вправа 3. Тека ports/02-retransmissions/, порт 9102.

Суть: у Linux-контейнері на lo вмикаємо 5% випадкових втрат і 5 мс затримки в кожен бік (tc netem), curl завантажує файл 2 МБ, tcpdump пише pcap. Wireshark сам підписує обидва способи помітити втрату: дубльовані ACK → швидкий повтор (≈ 1 RTT) і таймер RTO (≥ 200 мс у Linux).

1. Як запустити

Перед парою

  • Docker (на macOS: Docker Desktop). sudo не потрібен.
  • Образ збирається один раз і потребує інтернету (≈ 1–2 хв). Запустіть ./run_demo.sh один раз удома; на парі він працює ≈ 10 с без мережі. Перевірка: docker image ls demo02-retrans.
  • Wireshark на Mac (на цьому Mac уже є в /Applications; інакше brew install --cask wireshark). Відкрити pcap можна без sudo.
  • Корисно у Wireshark: Preferences → Protocols → TCP → Calculate conversation timestamps, щоб мати поле tcp.time_delta (пауза від попереднього кадру з'єднання).

Варіант А: одна команда (macOS або Linux)

cd ports/02-retransmissions
./run_demo.sh                    # 5% втрат, 2 МБ, SACK увімкнено → capture.pcap
open -a Wireshark capture.pcap   # macOS;  Linux: wireshark capture.pcap &

Скрипт сам будує образ (якщо його немає), запускає контейнер demo02-retrans з --cap-add NET_ADMIN, усередині виконує inside.sh і друкує чотири блоки: налаштування lo, завантаження, лічильники ядра (nstat), підсумок «як побачить Wireshark» (analyze.py). Тека змонтована в контейнер, тому capture.pcap одразу з'являється поруч.

Змінні середовища (перевірено в run_demo.sh / inside.sh):

ЗміннаЗа замовч.Навіщо
LOSS5%LOSS=10% ./run_demo.sh: RTO майже гарантовано

Аналіз pcap можна запустити й на самому Mac (бере tshark з Wireshark.app, перевірено з 4.6.9):

python3 analyze.py sample_sack.pcap
python3 analyze.py capture.pcap --tshark /Applications/Wireshark.app/Contents/MacOS/tshark

Ключі analyze.py: --examples N (скільки прикладів показати, 4), --rto-gap 0.2 (поріг паузи, після якої повтор вважаємо RTO).

Варіант Б: крок за кроком на очах у студентів (Docker)

Ті самі кроки, що в inside.sh, але вручну. Цю послідовність проганяли під час підготовки (розділ E у expected_output.txt).

# термінал 1: довгоживучий контейнер, «ламаємо» його loopback
docker run -d --rm --name demo02-live --cap-add NET_ADMIN -v "$PWD":/demo demo02-retrans sleep infinity
docker exec demo02-live bash -c '
  ip link set lo mtu 1500
  ethtool -K lo tso off gso off gro off
  ip link set lo gso_max_segs 1
  tc qdisc add dev lo root netem delay 5ms loss 5%
  tc qdisc show dev lo
  mkdir -p /srv && head -c 2M /dev/urandom > /srv/file.bin'
docker exec -d demo02-live python3 -m http.server 9102 --bind 127.0.0.1 --directory /srv
docker exec -d demo02-live tcpdump -i lo -n -U -w /demo/live.pcap 'tcp port 9102'

# термінал 2: «позначки Wireshark» наживо, лише цікаві кадри
docker exec -it demo02-live tshark -l -i lo -f 'tcp port 9102' \
    -Y 'tcp.analysis.flags && !tcp.analysis.window_update'

# термінал 1: завантаження (прогрес curl «завмирає» на RTO)
docker exec demo02-live curl -o /dev/null http://127.0.0.1:9102/file.bin
docker exec demo02-live nstat -z TcpRetransSegs TcpExtTCPFastRetrans TcpExtTCPTimeouts

# кінець
docker exec demo02-live pkill tcpdump
open -a Wireshark live.pcap
docker rm -f demo02-live
Увага: macOS
  • На macOS немає tc/netem. Аналоги (dummynet dnctl + pfctl, Network Link Conditioner) потребують sudo і не перевірялися, тому демо працює в Docker.
  • Docker Desktop запускає Linux-VM (ядро 6.12.76-linuxkit), тож студенти бачать TCP Linux, а не стек macOS.
  • netstat -s -p tcp на Mac без sudo показав одні нулі. Лічильники беріть з nstat у контейнері.
  • Варіант на «голому» Linux з sudo (ті самі команди на lo хоста) не тестувався; він сповільнює весь loopback машини, доки не відкотите tc qdisc del dev lo root тощо.

Запасний план (1 хвилина, без Docker)
  1. open -a Wireshark sample_sack.pcap: справжній записаний трафік. run_demo.sh пише в capture.pcap і зразки не перезаписує (тільки не передавайте PCAP=sample_sack.pcap).
  2. Фільтр frame.number <= 27: діра, Dup ACK #1…#7 із SACK-блоками, швидкий повтор.
  3. Фільтр frame.number >= 102 && frame.number <= 111: два RTO (+0.244 с, +0.288 с), кожен з D-SACK.
  4. Analyze → Expert Information: підсумки.
  5. Без Wireshark: expected_output.txt, розділ A (термінал) і розділ E (живий tshark, кадри 169 → 170).

2. Що означає вивід

Усі числа нижче з реальних запусків (expected_output.txt, sample_sack.pcap). Втрати випадкові: у кожному запуску числа інші, стабільні лише категорії подій.

2.1 Де губиться пакет і що бачить tcpdump

netem стоїть на виході lo, а на loopback обидва напрямки йдуть через цей вихід: губляться і сегменти з даними, і ACK. tcpdump бачить пакет після netem, тож загублений сегмент у pcap не потрапляє взагалі. Видно лише діру, яку він лишив, і потім повтор. Тобто pcap показує погляд отримувача.

Чому MTU 1500: на lo за замовчуванням MTU 65536, сегмент ≈ 64 КБ, і на 2 МБ лише 73 кадри та 1–2 події (розділ D). З MTU 1500 сегмент 1448 байтів (MSS 1460 мінус 12 байтів TCP timestamps), як в Ethernet, і подій десятки. gso_max_segs 1 потрібен, бо netem губить цілий буфер ядра: без нього один «випадковий» дроп забирав до 21 сегмента поспіль.

Кожен рядок це фільтр відображення Wireshark і скільки кадрів під нього підпало (sample_sack.pcap, tshark 4.6.9 на Mac, розділ B):

     60  tcp.analysis.lost_segment                   ← діра в seq: сегмент загубився
    183  tcp.analysis.duplicate_ack                  ← усі Dup ACK
     39  tcp.analysis.duplicate_ack_num == 3         ← саме третій дубль
    223  tcp.options.sack_le                         ← ACK із блоками SACK

2.4 Спосіб 1: дублі ACK і швидкий повтор (кадри 6–26)

Перевірено tshark 4.6.9 на sample_sack.pcap (у expected_output.txt рядки обрізані до 100 символів, тому SLE/SRE там не видно):

  6 0.021  9102 → 52956 [PSH, ACK] Seq=1 Len=206                       ← заголовок HTTP-відповіді
  7 0.021  [TCP Previous segment not captured] Seq=1655 Len=1448     ← байтів 207–1654 немає
 12 0.021  [TCP Previous segment not captured] Seq=10343             ← друга діра: 8895–10342
 14 0.027  52956 → 9102 [ACK] Ack=207                                ← «чекаю байт 207»
 15 0.027  [TCP Dup ACK 14#1] Ack=207 SLE=1655 SRE=3103              ← «досі чекаю 207, але 1655–3102 вже є»
 16 0.027  [TCP Dup ACK 14#2] Ack=207 SLE=1655 SRE=4551
 17 0.027  [TCP Dup ACK 14#3] Ack=207 SLE=1655 SRE=5999              ← класичний третій дубль
 ...
 20 0.027  [TCP Dup ACK 14#6] Ack=207 SLE=10343 SRE=11791 SLE=1655 SRE=8895   ← 2 блоки = 2 діри
 21 0.027  [TCP Dup ACK 14#7] Ack=207 SLE=10343 SRE=13239 SLE=1655 SRE=8895
 26 0.033  [TCP Fast Retransmission] Seq=207 Len=1448               ← ≈ 6 мс після дублів
 46 0.057  [TCP Fast Retransmission] Seq=8895 Len=1448               ← друга діра, знайдена через SACK
  • Кадр 7: Wireshark бачить втрату раніше, ніж будь-який ACK, бо номер seq «стрибнув» (після 1+206 мав бути 207, а прийшов 1655).
  • Ack=207: ACK кумулятивний, «маю все до 206, далі шли 207». Кожен наступний сегмент після діри змушує отримувача повторити той самий Ack: це і є Dup ACK. Запис 14#3 = третій дубль ACK-кадру 14.
  • SLE/SRE (SACK Left/Right Edge): які діапазони після діри вже прийшли. Дозволяє відправнику полатати кілька дір за один RTT. Обидві сторони погодили SACK у рукостисканні (SACK_PERM у SYN і SYN-ACK).
  • Чому повтор аж у кадрі 26: дублі йдуть до відправника пів RTT, повтор назад ще пів RTT (затримка 5 мс у кожен бік), тож у pcap він з'являється через ≈ 6 мс.
Увага: «рівно після 3 дублів» не обіцяйте

Сучасний Linux рахує не дублі, а скільки даних отримувач підтвердив за діркою (SACK, RFC 6675) плюс часовий RACK. У реальних записах буває:

  • повтор до Dup ACK #3: живий запуск, кадр 112 після лише #2, бо SACK вже показав ≈ 32 сегменти за діркою (розділ E);
  • повтор після Dup ACK #18: sample_nosack.pcap, кадри 187–216. Відправник вирішив раніше, але дублі вже летіли, а повтору ще 6 мс до точки захоплення.

Для слайда правило «3 дублі ACK» правильне, просто без «рівно на третьому».

2.5 Спосіб 2: таймер RTO (кадри 102–111)

102 0.176  52956 → 9102 [ACK] Ack=79847
103 0.182  9102 → 52956 Seq=79847 Len=1448                     ← обидва сегменти ДІЙШЛИ…
104 0.182  9102 → 52956 Seq=81295 Len=1448                     ← …але їхні ACK загубилися
105 0.426  [TCP Retransmission] Seq=79847   (+0.244)          ← тиша 0.244 с: спрацював RTO
106 0.432  [ACK] Ack=82743 SLE=79847 SRE=81295               ← D-SACK: «це в мене вже було»
 ...
109 0.450  [TCP Out-Of-Order] Seq=82743                      ← швидкий повтор, Wireshark назвав його Out-Of-Order
110 0.738  [TCP Retransmission] Seq=82743   (+0.288)          ← його ACK теж загубився: знову RTO
111 0.744  [ACK] Ack=85639 SLE=82743 SRE=84191               ← знову D-SACK
  • (+0.244): tcp.time_delta, пауза від попереднього кадру з'єднання. RTO = SRTT + 4·RTTVAR (RFC 6298), але не менше мінімуму: RFC радить 1 с, Linux бере 200 мс. При RTT ≈ 12 мс RTO фактично ≈ 200 мс з хвостиком. У всіх запусках паузи перед RTO були 0.21–0.29 с.
  • D-SACK (у Wireshark Warn «D-SACK Sequence»): блок SACK нижче за Ack, тобто «ці байти я вже мав». RTO був хибним: дані дійшли, губилися ACK.
  • Після RTO TCP вважає мережу сильно перевантаженою: cwnd → 1 сегмент, повільний старт заново, а при повторних таймаутах RTO подвоюється.

3. На чому наголосити

Ключові думки
  1. Два способи помітити втрату. Дублі ACK: швидко, ≈ 1 RTT (тут ≈ 6–12 мс). Таймер RTO: повільно, ≥ 200 мс у Linux. Різниця в 20+ разів видна прямо в колонці часу.
  2. Таймер це страховка для випадків, коли дублів не буде: загубився сам повтор (кадри 169 → 170), загубилися всі ACK (кадр 105), втрата в хвості пачки (спершу TLP).
  3. Втрата б'є по швидкості набагато сильніше, ніж по байтах. 5% втрат, а завантаження у ≈ 15 разів довше (0.36 → 5.36 с): кожна втрата зменшує cwnd удвічі, кожен RTO скидає його до 1 сегмента.
  4. SACK каже відправнику, що саме дійшло після діри, і дозволяє латати кілька дір за RTT. Без нього RTO частіші (3 проти 12 у наших прикладах).
  5. Wireshark здогадується. Позначки обчислено з трасування, а не прочитано з пакета; звіряйте з паузою tcp.time_delta і лічильниками ядра.
«Ага»-момент

Кадри 169 → 170 у живому запуску (або 103–106 у зразку): той самий seq двічі, між ними тиша ≈ 0.22–0.24 с, і прогрес curl стоїть. Студенти бачать, що «повільний» спосіб існує саме тому, що «швидкий» іноді не може спрацювати. А D-SACK у кадрі 106 показує, що дані взагалі не губилися: губилися ACK.

Питання до аудиторії

Хто першим помічає втрату: відправник чи отримувач?
Отримувач, за стрибком seq (кадр 7). Але виправити може лише відправник, і дізнається він через ACK.
Чому чекати 3 дублі ACK, а не один?
Пакети можуть приходити не по порядку. Один-два дублі можуть означати «трохи запізнився»; три це компроміс між швидкістю і хибними тривогами.
Чому швидкий повтор «швидкий»?
Він чекає ≈ 1 RTT, а не ≥ 200 мс таймера. Хай знайдуть паузу ≥ 0.2 с у tcp.time_delta.
Коли дублі ACK не допоможуть?
Загублено останній сегмент, загублено сам повтор (169 → 170), загублено всі ACK (105). Лишається таймер.
Що SLE/SRE дає відправнику понад Ack?
Які діапазони після діри вже є: можна полатати кілька дір за раз і не слати зайве.
5% втрат, чому ж у 15 разів повільніше?
Втрата для TCP це сигнал перевантаження: cwnd зменшується, після RTO повільний старт заново. Це коштує набагато більше, ніж повторні байти.
Кожен «TCP Retransmission» у Wireshark це таймаут?
Ні. Wireshark так підписує будь-який повтор без попередніх дублів, зокрема TLP і RACK. Таймаут: пауза ≥ 0.2 с і лічильник TcpExtTCPTimeouts.

Вправа 3

Дайте студентам sample_sack.pcap і попросіть порахувати фільтрами дублі ACK, швидкі повтори і RTO. Відповіді (Wireshark 4.6.9): tcp.analysis.duplicate_ack = 183, tcp.analysis.fast_retransmission = 34, RTO (tcp.analysis.retransmission && !tcp.analysis.fast_retransmission && tcp.time_delta >= 0.2, потрібні conversation timestamps) = 3. Якщо у студента інша версія Wireshark, «інші повтори» й Out-Of-Order можуть відрізнятися; ці три числа ні.

Які хибні уявлення виправляє демо

  • «Загублений пакет видно в Wireshark». Ні: видно лише діру після нього (Previous segment not captured) і повтор.
  • «Повтор завжди рівно після третього дубля». У Linux із SACK/RACK буває і після другого, і після вісімнадцятого.
  • «RTO означає, що дані загубилися». Тут усі 3 RTO були хибні: губилися ACK, і D-SACK це підтверджує.
  • «5% втрат = на 5% повільніше». У ≈ 15 разів повільніше.
  • «5% випадкових втрат = поодинокі втрати». Ядро губить цілі буфери, тож без gso_max_segs 1 один дроп забирав до 21 сегмента поспіль.
