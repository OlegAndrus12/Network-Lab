1. What the demo shows

One sender ticks a clock every 100 ms: each tick is "<seq> <unix time>\n", sent both as a UDP datagram to port 9104 and over a TCP connection to port 9114. Linux netem drops 10% of packets and delays each by 50 ms. The receiver prints the two streams side by side, one screen row per 100 ms of wall time:

  • UDP (left) keeps ticking steadily at about 51 ms lag. Lost ticks show up as ··· пропущено N тіків ···, and the clock never stops.
  • TCP (right) loses nothing, but whenever one segment is lost the column goes silent (‖ ЗАМЕРЗЛО на 300 мс). Then 3 to 10 ticks land in the same millisecond (← пачка) with lag bars of 250 to 850 ms. That is head-of-line blocking, visible on screen.

Supports: the slide «Застарілі дані гірші за втрачені», exercise 5, and the TCP vs UDP comparison slide. For a clock, a game position or a voice frame, a tick that arrives 600 ms late is worse than one that never arrives, because it also holds back every newer tick behind it.

2. The mechanism: what happens inside TCP and the kernel

UDP: every datagram stands alone

Each sendto() becomes one datagram. If netem drops it, nothing in the kernel notices or retries. The next datagram is delivered to recvfrom() as soon as it arrives. The application sees the loss only because our payload has a sequence number (UDP has none), which is how the receiver prints пропущено.

TCP: an ordered byte stream

  1. Stream, not messages. TCP delivers bytes, not ticks, so the receiver needs framing. We end each tick with \n and split on it. TCP_NODELAY turns off Nagle so each 21-byte tick leaves as its own segment instead of waiting to be coalesced.
  2. In-order delivery. When segment N is lost but N+1, N+2 arrive, the receiving kernel keeps them in its out-of-order queue. recv() may only return bytes up to the first hole, so the application is blocked even though newer data is already sitting in kernel memory. In our ss -tni snapshot the receiver had rcv_ooopack:12, meaning 12 segments had been parked out of order 7 s into an 8-second run.
  3. Loss detection. Each later segment triggers a duplicate ACK carrying a SACK block (verified in the capture: sack 1 {61:101}). Linux's RACK/SACK logic then decides the hole is a loss and retransmits. When that fails (the retransmission is lost too, or no later data exists to trigger SACKs, as at the end of the stream), recovery falls back to timers: tail-loss probe and finally the RTO. The RTO has a 200 ms floor on Linux (TCP_RTO_MIN) and doubles on each retry.
  4. The burst. When the retransmission fills the hole, the kernel hands the whole contiguous range to the next recv() at once. That is why several ticks print with identical receive times and lags decreasing in 100 ms steps (352, 252, 152, 52 ms).

Why the stalls are about 300 ms (worked timeline from the capture)

t (ms)Event
0Tick N sent, dropped by netem
100Tick N+1 sent; arrives at 150; receiver sends a dup ACK with SACK
200Dup ACK reaches the sender (another 50 ms); RACK marks N lost and retransmits at once
250Retransmission arrives; ticks N and N+1 are released together. Lag of N = 250 ms

Stuck lag ≈ tick interval + RTT + one-way delay = 100 + 100 + 50 = 250 ms, which matches the many #… 25x мс lines. The receiver had seen nothing since t = −50, so the visible stall is about 300 ms. If the first dup ACK is also lost (10% loss applies to ACKs too), the sender waits for the next one: 350 ms lag and a 400 ms stall, which the tcpdump excerpt shows. A lost retransmission pushes TCP onto the RTO with backoff, giving the 600–900 ms stalls and, at the very end of one run, 2030 ms.

Why add 50 ms delay? netem on lo touches each packet once, so 50 ms means one-way 50 ms and RTT about 100 ms (ss: rtt:102). Without delay (a DELAY=0ms run), RTT is about 0 and the sender retransmits as soon as the next tick's SACK arrives. Stalls were then 200–225 ms, often just one tick, and the lag baseline was 0 ms, so a stall looked like a blip (5 stalls in 10 s, max 441 ms). With 50 ms delay the stall comes out at 300 ms or more, the "normal" lag is a clear 51 ms baseline to compare against, and it looks like a real WAN path.

Correction to the common "min RTO 200 ms" explanation: in these runs most stalls were not RTO timeouts. They were SACK/RACK fast recovery, which is clocked by the next tick. RTO shows up only for the longer stalls. Both mechanisms are worth naming.

3. Running it live

Before class (once, needs internet)

cd 04-clock-tcp-vs-udp
./run_demo.sh --duration 3     # builds the demo04-clock image (python:3.12-slim + iproute2, tcpdump)

Option A: one command (macOS or Linux with Docker)

./run_demo.sh                       # 15 s, delay 50ms, loss 10%, two columns
./run_demo.sh --duration 30         # longer
LOSS=20% ./run_demo.sh              # more drama if the run is too calm
DELAY=0ms ./run_demo.sh             # show why the delay matters
NO_DOCKER=1 ./run_demo.sh           # macOS, no netem: control experiment, both columns identical

It starts container demo04-clock-run with --cap-add NET_ADMIN, runs tc qdisc add dev lo root netem delay 50ms loss 10% and then clock.py. The container is removed on exit. Terminal width needs to be at least 84 columns. Colours appear only when stdout is a real terminal.

Option B: separate terminals (more visual: TCP and UDP receivers in different windows)

./run_demo.sh shell      # background container demo04-clock with netem already on lo
# Terminal 1
docker exec -it demo04-clock python3 clock.py recv --proto udp
# Terminal 2
docker exec -it demo04-clock python3 clock.py recv --proto tcp
# Terminal 3: both senders at once
docker exec -it demo04-clock sh -c 'python3 clock.py send --proto udp & python3 clock.py send --proto tcp; wait'
# optional: watch retransmissions
docker exec -it demo04-clock tcpdump -i lo -n -tttt 'tcp port 9114'
docker exec -it demo04-clock ss -tni '( sport = :9114 or dport = :9114 )'
./run_demo.sh stop       # when done

The TCP receiver exits by itself when the sender closes. Stop the UDP receiver with Ctrl+C, which prints its summary.

Inspecting sockets: macOS vs Linux

macOS (host, no loss)

lsof -nP -iTCP:9114 -iUDP:9104
netstat -an -p tcp | grep 9114
netstat -an -p udp | grep 9104
nettop -m tcp (live per-socket view)
macOS has no netem and no ss. Loss could in principle be emulated with dnctl/pfctl dummynet, but that needs sudo and was not tested for this demo.

Linux / Docker (with loss)

tc qdisc show dev lo
ss -tni '( sport = :9114 )' shows rtt, rto, retrans, rcv_ooopack
ss -unap | grep 9104
tcpdump -i lo -n 'tcp port 9114'
On a bare Linux host you could run sudo tc qdisc add dev lo root netem … directly, but that slows all loopback traffic on the machine. Use the container.

5. Things to point out or ask

  • Ask before running: "With 10% loss, which clock will look better?" Many students expect TCP to win because it is reliable.
  • Point at the right column during a stall: the data is already in the receiver's kernel. Who is holding it back, and why? (In-order delivery: recv() cannot skip a hole.)
  • Look at the burst lags (352, 252, 152, 52): TCP did deliver everything, but what is a 352 ms-old clock reading worth? That is the slide «Застарілі дані гірші за втрачені».
  • Medians are equal and maxima are not. Reliability costs latency in the tail, not on average.
  • Why did the code need \n framing and TCP_NODELAY for TCP but not for UDP? (Byte stream vs datagrams; Nagle.)
  • Why didn't lowering the RTT (DELAY=0) remove the stalls? (Loss detection still needs the next tick to arrive, or a timer with a 200 ms floor.)
  • Bridge to real protocols: VoIP/RTP, games and DNS use UDP. QUIC (HTTP/3) runs over UDP partly to avoid exactly this cross-stream head-of-line blocking. WebRTC data channels can be configured unordered and unreliable.
  • Exercise 5 tie-in: have students pick TCP or UDP for a live score ticker, a file download and a video call, and justify each using this output.

6. Gotchas and live recovery

  • Docker Desktop not running causes Cannot connect to the Docker daemon. Start Docker Desktop and wait for it to come up, or switch to the fallback.
  • First run needs internet for apt-get in the image build. Build before class; after that the image is cached.
  • A calm run. 10% loss is random, and a 15 s run sometimes has only a couple of short stalls. Re-run, use --duration 30, or LOSS=20%.
  • A long stall at the end (up to 2 s) is normal tail loss: no later ticks exist to trigger SACK, so only the RTO with backoff can recover. The script waits up to 5 s for TCP after the senders finish.
  • Startup. If the SYN is lost, the TCP connect retries after 1 s (initial RTO) and TCP starts behind with a burst. This is genuine but can confuse students; mention it or re-run.
  • Narrow terminal (under 84 columns) wraps the columns. Widen it or reduce the font size. If ■ ‖ ← render as boxes, switch to a font with box-drawing glyphs (Menlo and SF Mono both work).
  • "Container name already in use": run ./run_demo.sh stop and docker rm -f demo04-clock-run.
  • Port busy on macOS (NO_DOCKER mode): lsof -nP -iTCP:9114 -iUDP:9104, then kill the leftover process.
  • Plain macOS without Docker shows nothing interesting: loopback loses nothing, so both columns are identical at 0–1 ms. That is a useful control experiment, not a failure.
  • The netem rule lives only inside the container's network namespace. It never affects the laptop's own networking.
